Этот файл — источник состояния разработки проекта и заданий для новых сессий. Сначала прочитай [AGENTS.md](AGENTS.md) и необходимые разделы [SKILLS.md](SKILLS.md), затем разделы «Текущий статус», «Решения проекта», «Протокол работы» и весь текущий этап. Нельзя считать переписку предыдущего агента доступной: все существенные решения и результаты должны оставаться в репозитории.

Документ содержит все 18 этапов P01–P18, для каждого — работы, критерии и два промпта. В первую версию входят 17 этапов; P13 отложен пользователем (deferred) и не блокирует её приёмку. Навигация находится в [реестре этапов](#stage-index). Статус todo означает, что разработка этапа ещё не начата, а не что его описание отсутствует.

## Решения проекта

1. Разрабатывается исполняемый файл git-task; пользователь вызывает его как git task. Это расширение командной строки Git, не плагин Codex и не модификация исходного кода Git.
2. Первая версия предназначена для личной работы. Один план на репозиторий; несколько активных задач допустимы, но одна активная попытка задачи связана с одной веткой, а ветка — с одной активной задачей.
3. Начало работы: git task start <branch> без флагов выбора автоматически выбирает первый todo в текущем порядке плана, без меню. --id выбирает по точному полю id из JSON, --title — по точному полю title; --new создаёт новую задачу, --select явно включает меню. Имя ветки — обязательный позиционный аргумент; без него ошибка без изменений. Флаг -b и автоматическая генерация имени не поддерживаются.
4. Ветка по умолчанию создаётся от локальной target_branch, обычно main, независимо от текущего HEAD. --from явно переопределяет основание создания, но не цель завершения задачи. Нет скрытого fetch/pull или предварительного checkout main.
5. Завершение означает интеграцию работы в целевую ветку либо явное подтверждение пользователя. Это не проверка качества кода, тестирования или публикации продукта.
6. Автоматическое завершение первой версии: обычный merge и fast-forward, без вопросов пользователю о задаче. Поддержка squash, включая отдельный ручной сценарий его подтверждения, отложена; cherry-pick и неоднозначное переписывание истории также не должны давать ложное done. Общая команда complete остаётся для явного ручного изменения состояния, но не является обязательным обходным сценарием squash.
7. Новые задачи вставляются после последней по времени завершённой задачи. Несколько вставок после одного завершения сохраняют порядок добавления. При отсутствии завершений формируется начальная группа. Позднейшее завершение не переставляет уже существующий план. Есть явные move, --after, --before, --end.
8. Основной план, настройки и состояние задач хранятся в одном локальном файле .git-task/plan.json в корне рабочей копии. Каталог /.git-task/ исключается через локальный Git info/exclude, без изменения общего .gitignore. Служебная ветка, коммиты метаданных и отдельные config.json/tasks/<id>.json не создаются. План общий для переключаемых веток этой рабочей копии; для редактирования не нужны checkout, commit или stash. Git не хранит историю и не переносит этот файл обычными push/clone; нужны локальная резервная копия и экспорт.
9. Для Git используется установленный исполняемый файл через os/exec. Аргументы передаются отдельно; пользовательский ввод не превращается в shell-команду. Используются машинные форматы вывода, где это возможно.
10. На старте достаточно стандартной библиотеки Go: flag, encoding/json, os/exec, bufio, testing. Внешняя зависимость допустима при конкретной пользе и документированном обосновании; не вводить фреймворк заранее.
11. Нет фонового сервиса, обязательного интернета или аккаунта. Hooks не задают вопросов и не обращаются к сети. status и sync восстанавливают наблюдения, если hooks были пропущены.
12. Первая версия работает локально. Перенос между компьютерами и sync --remote отложены (P13); не реализовывать их CLI, transport или специальные проверки переноса до отдельного решения пользователя. Локальный sync остаётся: он сверяет задачи с локальной историей Git без сети. Обычный push фича-ветки не переносит план автоматически.
13. План импортируется из плоского Markdown-чеклиста. После импорта исходный Markdown не является вторым синхронизируемым источником истины. Полный перенос состояния предусмотрен через JSON.
14. Состояния задач продукта: todo, in_progress, paused, done, archived. Единственное каноническое значение JSON для не начатой задачи — "todo"; альтернативных написаний и алиасов статуса нет. Текущая работа хранится в active_attempt, а attempts содержит только завершённые подходы и впервые появляется при первом done. Повторный start с --again сохраняет attempts и переводит done прямо в in_progress; отдельной команды reopen нет.
15. Поддерживаемые платформы выпуска: Windows, Linux, macOS. Минимальные версии Go и Git выбираются по используемым возможностям и проверяются в CI. Не обещать поддержку непроверенных конфигураций.
16. Публикация релиза, изменения удалённого репозитория, глобальная установка и настройка системы не входят автоматически в выполнение этого плана. Готовить локально проверяемые результаты; внешние действия выполнять только при соответствующей авторизации пользователя.
17. Пользователь требует понятного разделения файлов/пакетов и соблюдения хороших Go-практик. Принятый эталон: Google Go Style Guide и рекомендации команды Go; GitHub CLI — практический ориентир для команд и ввода-вывода. Обязательные границы и применимость описаны в AGENTS.md и SKILLS.md. В internal/app допускается выделение общей координации сценариев, когда она нужна CLI и hooks; не создавать пустые слои заранее.
18. Перед завершением каждого задания с изменением поведения исполнитель пишет все необходимые тесты и запускает их. Тестирование не откладывается до P15; без успешных обязательных проверок этап не объявляется готовым к review. Проверяющий независимо воспроизводит необходимые проверки.

## Контракт локального хранения

- Единственный источник плана продукта — `.git-task/plan.json` в корне рабочей копии, не этот `PLAN.md` с заданиями разработки. В одном JSON находятся настройки, порядок и задачи; примеры отдельных задач ниже — фрагменты, не отдельные файлы. Точную схему фиксируют P03/P05.
- `init` создаёт файл только при безопасном свободном пути и добавляет `/.git-task/` в локальный `info/exclude`, путь к которому получает через Git. Повторная инициализация не сбрасывает данные. Исключение не снимает уже существующее отслеживание: такой конфликт требует явного решения пользователя, а не автоматической правки индекса.
- Изменение плана не требует переключения ветки, коммита кода или stash, даже при staged/unstaged изменениях кода. Обычные переключения между ветками, не отслеживающими `.git-task/`, используют один локальный план. Это не обещание синхронизации разных clone или linked worktree; границы поддержки дополнительных рабочих деревьев определить в P01.
- Запись через CLI/hooks использует общий механизм блокировки, проверки прочитанной версии, валидации и безопасной замены. Рядом допустимы локальные lock, журнал, временный файл и последняя валидная резервная копия. Они не заменяют основной файл и не импортируются как второй план.
- JSON можно открыть в редакторе. Для редактирования с обнаружением конфликта предпочтительна команда edit; произвольный внешний редактор не соблюдает блокировку плагина. При обнаружении внешнего изменения или невалидного файла нельзя молча перезаписывать данные. Не обещать защиту от любой одновременной записи внешнего редактора.
- Резервная копия помогает при прерванной записи, но не заменяет внешнее резервирование: удаление всей `.git-task/`, в том числе очисткой игнорируемых файлов, может удалить и план, и копию. Обычные push/clone их не переносят. Export сохраняет отдельный пользовательский снимок; удаление интеграции не удаляет данные.

## Контракт start и attempts

Этот раздел фиксирует уточнение пользователя и обязателен для P01/P03/P06–P12 и их проверок. Старые предложения о меню по умолчанию, основании от текущего HEAD и добавлении незавершённой попытки в attempts больше не действуют.

Пользователь выбрал два флага явного поиска существующего пункта: --id и --title. Прежний флаг выбора задачи удалён из актуального интерфейса; дополнительные алиасы не вводятся. Оба способа используют одну операцию запуска и одинаково поддерживают --again.

### Выбор задачи и создание ветки

| Команда | Выбор задачи | Имя новой ветки |
|---|---|---|
| git task start | Ошибка: требуется имя ветки; выбор и запись не выполняются | Не создаётся |
| git task start feature | Первый todo по порядку плана | feature |
| git task start feature --id task-003 | Задача с JSON id="task-003" | feature |
| git task start --id task-003 | Ошибка: требуется имя ветки, даже с селектором | Не создаётся |
| git task start feature --title "Добавить профиль" | Единственная задача с таким JSON title | feature |
| git task start --title "Добавить профиль" | Ошибка: требуется имя ветки, даже с селектором | Не создаётся |
| git task start feature --id task-003 --again | Повторный запуск завершённой задачи по id | feature |
| git task start feature --title "Добавить профиль" --again | Повторный запуск завершённой задачи по title | feature |
| git task start feature --new "Авторизация" | Новая задача с указанным title | feature |
| git task start feature --select | Явное меню выбора/создания | feature |

1. Первый todo определяется массивом порядка плана, а не минимальным ID и не положением текущей ветки. Done, in_progress, paused и archived пропускаются. Несколько задач могут одновременно быть in_progress.
2. --id принимает точное строковое значение поля id из JSON. Ни позиция в плане, ни поле number, ни числовое сокращение не подставляются автоматически. Для id="task-003", number="T-003" подходит --id task-003, а --id 3 или --id T-003 не подходят, если нет другого пункта с буквально таким id. Move и edit title не меняют ID.
3. --id, --title, --new и --select взаимоисключающие. Одновременные --id и --title дают ошибку даже для одной задачи; неоднократное указание одного селектора также ошибка. Указанный пункт не заменяется другим. Для done обычный start возвращает ошибку с подсказкой команды с тем же селектором и --again; повторный запуск допускается по любому из двух селекторов. Для paused — resume; для in_progress запрещена вторая активная ветка. Attach не возобновляет done молча.
4. Если todo нет, автоматический start сообщает «Нет не начатых задач» и ничего не меняет. Он не открывает меню сам, не возобновляет done/paused и не создаёт новую задачу без --new.
5. Имя ветки обязательно: ровно один непустой позиционный аргумент branch во всех режимах, включая --id/--title/--new/--select/--again. Нет имени, лишние позиционные аргументы или -b — ошибка с примером git task start feature до диалога и любых мутаций. Имя и суффиксы не генерируются. Свободность имени перепроверяется при создании; гонка обрабатывается безопасно.
6. Если явно указанное имя feature уже существует, start выдаёт ошибку без изменения плана. Он не переиспользует и не переименовывает чужую ветку. Для существующей ветки предназначен attach.
7. Основание по умолчанию — актуальный локальный ref target_branch. Если он отсутствует, ошибка без мутаций; не заменять его текущим HEAD. --from переопределяет только основание. Данные могут быть локально устаревшими относительно сервера — инструмент не подтягивает их незаметно.
8. Выбор задачи, свободность ветки и доступность основания перепроверяются перед записью. Ошибка или отмена до создания ветки не переводит ни todo, ни done в in_progress. Прерывание после фактического создания ветки обрабатывается журналом восстановления; исходный статус и история сохраняются в журнале, отдельного перехода через todo нет.
9. Автоматический start работает и без интерактивного терминала. Только --select требует возможности диалога. title и имя ветки независимы: пользователь задаёт имя ветки, оно не переименовывает задачу.
10. --again требует ровно один явный селектор (--id или --title) и статус done. С todo/in_progress/paused/archived, без селектора или вместе с --new/--select возвращается ошибка без изменений. Флаг не означает force: не обходит неоднозначность title, занятое имя, грязное рабочее дерево, ошибки Git или проверки привязок. Имя новой ветки обязательно и в повторном запуске.
11. --title принимает полное точное значение поля title, с учётом регистра, пробелов и Unicode; нет поиска подстроки, обрезания пробелов или неявной нормализации. Кавычки оболочки группируют заголовок с пробелами в один аргумент и не являются частью значения. Пустое/состоящее только из пробелов значение — ошибка. Поиск идёт по всем задачам до проверки статуса, чтобы совпадение не менялось из-за завершения или архивирования.
12. Если заголовок отсутствует — ошибка «Пункт с таким title не найден» без создания новой задачи. Если найдено несколько совпадений — ошибка неоднозначности, список подходящих id и предложение использовать --id. Одинаковые заголовки разрешены в плане, но первый совпавший не выбирается автоматически, в том числе с --again.
13. После поиска по title дальнейшая работа привязывается к постоянному id, а не к тексту. Переименование не разрывает существующую связь; последующий поиск использует актуальный title. До мутации перепроверить выбранный пункт и его версию, не перенаправлять начатую операцию на другую задачу при конкурентном изменении.
14. Все документированные примеры с флагами после имени ветки должны работать, включая `git task start feature --id task-003 --again`. Выбор стандартного flag не разрешает молча проигнорировать аргументы после первого позиционного: это отдельная обязательная проверка CLI.

### Повторный запуск завершённого пункта

~~~text
$ git task start feature --id task-003
Ошибка: T-003 «Добавить профиль» уже выполнена.
Чтобы начать новый подход, добавьте --again:
  git task start feature --id task-003 --again
~~~

Первый вызов возвращает ненулевой код выхода, не создаёт ветку и не меняет status/attempts. Повторный вызов с --again создаёт новую ветку от target_branch, новый active_attempt и сразу меняет done → in_progress. Старые attempts сохраняются без добавления записи до нового завершения. После успешного запуска повтор того же вызова не создаёт ещё один подход: пункт уже in_progress. Сам флаг --again — явное подтверждение пользователя; дополнительный вопрос «открыть заново?» и отдельная команда не нужны.

Для той же задачи с title="Добавить профиль" эквивалентен вызов git task start feature --title "Добавить профиль" --again, если этот заголовок уникален. Title выбирает уже существующую задачу; создание новой по-прежнему выполняет --new.

Примеры пользовательского поведения:

~~~text
До:    T-001 done, T-002 in_progress, T-003 todo
Ввод:  git task start feature-profile
После: T-001 done, T-002 in_progress, T-003 in_progress
Ветка: feature-profile, создана от target_branch (например, main)

До:    T-001 done, T-002 todo, T-003 todo
Ввод:  git task start feature --id task-003
После: T-001 done, T-002 todo, T-003 in_progress

Затем: git task start feature-2
~~~

### Текущая работа и завершённые подходы

- До первого завершения поле attempts отсутствует, а не содержит пустой массив или незавершённую запись.
- Успешный start/attach создаёт active_attempt с собственным ID, связью с веткой и наблюдениями; задача становится in_progress. Это поле необходимо для tracking до merge. Оно не является записью в attempts.
- При доказанном слиянии в target_branch одним обновлением метаданных: status становится done, завершённая запись добавляется в attempts, active_attempt удаляется. Повторный hook/sync не добавляет ту же запись снова; ключ — ID активного подхода, не только SHA.
- Каждый done содержит непустой attempts. При ручном complete или импорте [x] также создаётся честная запись с основанием manual/imported; неизвестные ветка, время начала и commit не выдумываются. Импортированная отметка не выдаётся за доказанное слияние.
- Успешный start с явным --id или --title и флагом --again создаёт новый active_attempt, меняет done → in_progress и сохраняет attempts без новых записей. Перехода через todo и команды reopen нет. При следующем завершении новая запись дописывается в attempts.
- Pause сохраняет active_attempt и attempts; resume продолжает тот же подход. Archive сохраняет историю по контракту модели и не добавляет фиктивное завершение.
- Поэтому наличие attempts означает «задача хотя бы раз завершалась», а не обязательно «она сейчас done». После повторного запуска attempts остаётся при in_progress и последующей паузе/архивировании.

Упрощённый пример первого запуска (служебные поля наблюдений не показаны):

~~~json
{
  "id": "task-003",
  "number": "T-003",
  "title": "Добавить профиль",
  "status": "in_progress",
  "active_attempt": {
    "id": "attempt-001",
    "branch": "feature-profile"
  }
}
~~~

После доказанного завершения:

~~~json
{
  "id": "task-003",
  "number": "T-003",
  "title": "Добавить профиль",
  "status": "done",
  "attempts": [
    {
      "id": "attempt-001",
      "branch": "feature-profile",
      "completion": {
        "source": "merge",
        "target_branch": "main"
      }
    }
  ]
}
~~~

В реальных данных дополнительно хранится достаточное доказательство по P09, включая необходимые commit ID. Примеры объясняют присутствие полей, а не заменяют полную схему P03/P05.
