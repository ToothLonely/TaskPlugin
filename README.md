# Git Task

`git task` связывает задачи с Git-ветками и помогает вернуться к работе.
Это небольшой Go CLI: Git запускает установленный `git-task` из PATH.
Пользовательский интерфейс — на русском. Go нужен только для сборки исходников.

Локальный кандидат: **0.1.0-rc.1**, схема плана 2. Он не опубликован и ещё
не прошёл окончательную приёмку. Windows, Linux и macOS на amd64 — целевая
матрица; кросс-сборка не подтверждает исполнение. Результаты и открытые проверки
находятся в [PLAN.md](PLAN.md), матрица — в [CHECKS.md](docs/CHECKS.md).
По решению пользователя от 2026-10-05 native Linux/macOS и Windows symlink
отложены в TODO-04: их исполнение пока не подтверждено. Приёмка P17 опирается
на доступные Windows-проверки; полный финальный набор остаётся P18.
Минимальная выбранная база — Git 2.51.0; для разработки Go 1.26.0.
Внешних Go-зависимостей нет. Для hooks нужны sh/mktemp/cat/rm, на Windows
они поставляются с Git for Windows. Git, его транспорт и авторизация
устанавливаются отдельно. ARM64 пока не заявлен.

## Личный режим

В обычном репозитории с начальным коммитом выберите существующую локальную
целевую ветку. Ниже это `main`; для репозитория с `master` укажите `master`.

```text
git task init --target main
git task add "Добавить экран поиска"
git task hooks install
git task start feature/search
```

`start <branch>` выбирает первый `todo` и создаёт новую ветку от локальной
`target_branch`, независимо от текущего HEAD. Имя ветки обязательно, занятое
имя отклоняется; `-b` и генерации имени нет. Рабочее дерево для переключения
должно быть чистым. `--from <ref>` меняет основание, но не цель завершения.
Явный выбор:

```text
git task start feature/search --title "Добавить экран поиска"
git task start feature/search --id <точный-id-из-JSON>
git task start feature/search --select
git task start feature/new --new "Новая задача"
```

Эти варианты альтернативные: выберите один. `--title` ищет точное уникальное
название, при дублях нужен `--id`. Номер в списке не равен JSON ID.
Только `--select` открывает меню и требует терминал.

Сделайте обычные коммиты своей работы и влейте ветку в target:

```text
git switch main
git merge feature/search
git task status
```

Hooks и локальная сверка распознают обычный merge и fast-forward при наличии
доказательств работы текущего подхода. Пустая/удалённая ветка или старый
достижимый коммит не доказывают завершение. Squash, cherry-pick и неоднозначно
переписанная история не дают автоматического `done`. Подробности —
[TRACKING.md](docs/TRACKING.md). `done` не подтверждает качество кода.

```text
git task status --json
git task show --id <task-id>
git task pause --id <task-id> --attempt <attempt-id>
git task resume --id <task-id> --attempt <attempt-id>
git task start feature/search-v2 --id <task-id> --again
```

`--again` нужен для нового подхода завершённой задачи; история и прежние ID
сохраняются. Ручное создание ветки не назначает задачу. Существующую локальную
ветку можно назначить через `attach <branch> --id <task-id>` без checkout.
`complete --id <task-id> [--attempt <attempt-id>] [--yes]` — явное ручное
завершение с основанием `manual`, а не доказательство Git-интеграции.
Для pause/resume/complete/rebind при неоднозначности требуется точный ID
подхода. Без него выбирается единственный локально связанный незавершённый
подход. Чужая опубликованная ветка автоматически локальной связью не становится.

## Где хранится план

Один рабочий `.git-task/plan.json` общий для переключаемых веток данной копии.
`init` добавляет `/.git-task/` в локальный `info/exclude`, сохраняя чужие записи.
План не добавляется в индекс кода, `.gitignore` не меняется. Локальные backup,
lock и журналы операций находятся рядом. Повторный init не сбрасывает данные.
Tracked/чужой путь, повреждение и наблюдаемая конкурентная правка дают отказ.
Дополнительные worktree, bare, shallow и partial clone для рабочего CLI
не поддерживаются. Прямой редактор не соблюдает блокировку CLI.

Плоский Markdown-чеклист импортируется в пустой инициализированный план:

```text
git task import tasks.md --yes
git task export --format json --output snapshot.json
```

Markdown после импорта не синхронизируется. JSON-экспорт сохраняет общий
снимок задач/подходов, но исключает локальные наблюдения, очередь и настройки
подключения; это не backup offline-очереди. Существующий output не перезаписывается.
Форматы — [TRANSFER.md](docs/TRANSFER.md).

## Подключаемый командный режим

В каждом clone режим включается явно. Уже должен быть настроен нужный Git
remote и Git author; используйте свою обычную Git identity. Новые подходы
получают author из `git var GIT_AUTHOR_IDENT`. Author — подпись происхождения,
не ACL и не проверенная сервером личность.

В свежем полном clone (также для второго участника):

```text
git task init --target main
git task team connect --remote origin
git task hooks install
git task status
```

`connect` получает существующий общий план, а при отсутствии служебной ветки
пытается опубликовать текущий. Для существующего старого плана сначала выполните
`migrate`, а не удаляйте `.git-task`. Hooks устанавливаются отдельно в каждом
clone; используйте бинарник по постоянному пути.

Общая копия — отслеживаемый `plan.json` в отдельной ветке **git-task-plan** того
же remote. Служебная история содержит метаданные без кода, её нельзя вливать
в target. Обмен планом не переключает рабочую ветку и не выполняет pull кода.
Не изменяйте служебную историю вручную и не используйте force push.

Участники могут одновременно начать одну задачу через `--id`/`--title`:
каждый подход получает устойчивый случайный ID, author и собственный status.
Задача `done` только когда **непустой набор всех известных подходов** имеет
status `done`. Завершение одного не завершает остальные. Поздно доставленный
offline-подход может вернуть `done` в `active`; CLI сообщает уведомление.
Позиционные номера при объединении могут изменяться, устойчивые ID — нет.

## Публикация, offline и повтор

После подключения add/start/attach/edit/move/pause/resume/complete/archive/import
пытаются опубликовать своё подтверждённое локальное действие. Перед push
получается свежая служебная база; независимые изменения объединяются по ID.
Обычная гонка обновления remote повторяется без вопроса: до трёх попыток
в пределах 30 секунд. Несовместимая правка одного поля диагностируется,
автоматического универсального resolver нет.

Отказ сети, прав сервера, лимит или отмена не отменяют уже записанную работу.
Для автопубликации выводится предупреждение «публикация не подтверждена,
локальная очередь сохранена» и команда продолжения. Успешная локальная
команда может вернуть 0 при таком предупреждении: это не подтверждение сервера.
`team publish` при собственном отказе возвращает ненулевой код. Git-операция
также могла уже совершиться до ошибки hook: сначала проверьте `doctor`/состояние.

```text
git task doctor
git task team publish
git task team fetch
git task status --json
```

После восстановления сети/прав выполняйте **team publish**, сохраняя прежнюю
очередь и ID. Не повторяйте start/complete ради доставки действия, не удаляйте
plan.json/журнал и не force-push. Потерянный ответ после успешного push
распознаётся по устойчивым ID/квитанциям; повтор не создаёт ещё один подход.
`team fetch` получает и применяет общий план, но очередь не публикует.
Проверьте диагностику и сведения об очереди в doctor/status: локальное
состояние и подтверждение публикации различаются. Само появление интернета
ничего не запускает; фонового сервиса нет.

## Fetch, pull и серверный merge

`status`, `sync` и собственные hooks не ходят в сеть и не задают вопросов.
Они могут записать локальные наблюдения и завершения, которые попадут в очередь.
Доставка происходит при следующем `team publish` или разрешённой пользовательской
мутации с публикацией; для предсказуемой явной доставки используйте publish.

Установленный `reference-transaction` применяет **уже полученную** служебную
remote-tracking ссылку. При обычном `git fetch`/`git pull` это работает только
если refspec remote получает git-task-plan. Универсального post-pull нет.
Merge/rebase/fast-forward, no-op или конфликт pull сами по себе не подтверждают
публикацию очереди. При узком refspec используйте `git task team fetch`.
Пропущенное событие ссылки восстанавливается следующими status/sync/hooks
из уже полученных данных, без вложенного fetch/push. Конфликт/lock выводится
как предупреждение; собственный hook не отменяет Git-операцию. Чужой hook
сохраняет свои аргументы, stdin и код выхода. Подробнее — [HOOKS.md](docs/HOOKS.md).

Merge на хостинге не вызывает локальный hook разработчика. Для управляемого
Git-сервера подготовлен отдельный post-receive и полный clone-worker:
[включение и ограничения](docs/P13-IMPLEMENTATION.md#серверное-включение),
пример в исходниках `scripts/git-task-post-receive.sample`. Он не установлен
автоматически; нужны права администратора сервера, запись git-task-plan,
доступ к свежим ссылкам кода и сохранённая ветка подхода до обработки.
Права push кода сами по себе не дают прав записи метаданных. Хостинг без
доступа к hooks требует отдельно настроенного задания; готовой интеграции
с произвольным SaaS нет. Успех push/merge кода не гарантирует успех метаданных.

## Миграция и восстановление

```text
git task migrate
git task doctor
git task doctor --repair recover-start --yes
```

Миграция схемы 1 → 2 явная: сохраняет историю/ID, исходные байты в
`plan.schema-1.json` и backup; старым подходам author не придумывается.
Незавершённая операция блокирует миграцию. Repair выбирайте по диагностике:
`recover-start`, `restore-backup` или `unlock`. Восстановление backup может
отбросить свежие неопубликованные данные; повреждённый оригинал сохраняется.
`--yes` пропускает вопрос, но не проверки. При конфликте нельзя затирать
одну сторону другой. Полный протокол — [DOCTOR.md](docs/DOCTOR.md).

Отложены squash, ACL, обязательное online-подтверждение назначения,
универсальное разрешение конфликтов и гарантированный планировщик доставки.
Uninstall удаляет интеграцию и выбранный бинарник, сохраняя локальный план,
очередь, общую ветку, код и чужие hooks: [INSTALL.md](docs/INSTALL.md).
Остальные команды: `git task help`, `git task help <command>`.
