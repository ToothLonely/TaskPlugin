# Git Task — правила работы агента

Эти инструкции относятся к проекту D:\TaskPlugin и его дочерним каталогам. Продукт — небольшой кроссплатформенный Go CLI git-task, вызываемый как git task. Владелец знаком с Android-разработкой, но не обязан знать Go: объясняй существенные решения простыми словами, при необходимости используя аналогию и указывая её пределы.

## Начало каждой задачи

1. Прочитай [PLAN.md](PLAN.md): текущий этап, следующую роль, общий протокол и журнал передачи.
2. Прочитай [SKILLS.md](SKILLS.md): разделы «Эталоны», «Архитектура» и инструкции для своего типа работы. Перед первым изменением Go-кода прочитай также «Идиоматичный Go» и «Проверки».
3. Изучи существующие файлы и состояние рабочей копии. Разработка начинается с P01; наличие документов само по себе не означает, что код уже существует.
4. Выполняй назначенный этап. Порядок передачи исполнитель → проверяющий и обновление статусов определяет PLAN.md. Не запускай дополнительных агентов без явного указания пользователя.

PLAN.md отвечает за требования и прогресс; AGENTS.md — за обязательные рабочие правила; SKILLS.md — за технические приёмы и эталоны. Не дублируй статус проекта в нескольких файлах. Прямые инструкции пользователя имеют приоритет; конфликт требований явно фиксируй, не разрешай его молчаливой сменой продукта.

SKILLS.md — проектное руководство, которое требуется читать по этой инструкции. Это не установленный пакет автоматически обнаруживаемых навыков; создавать .agents/.codex или глобально устанавливать skills ради его использования не требуется.

## Обязательный эталон качества

При написании и проверке Go-кода соблюдай применимые принципы [Google Go Style Guide](https://google.github.io/styleguide/go/guide), [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments) и [рекомендации команды Go по структуре модуля](https://go.dev/doc/modules/layout). Главный приоритет — понятный поток выполнения, простота и сопровождаемость. Это принятый стандарт проекта, а не утверждение, что корпоративное руководство Google является спецификацией языка.

Практический образец CLI — [GitHub CLI](https://github.com/cli/cli) и его [описание устройства](https://github.com/cli/cli/blob/trunk/docs/project-layout.md). Используй его для разделения команд, отделения аргументов от выполнения, явного ввода-вывода и тестируемых границ. Конкретные правила применения и ссылки на код находятся в SKILLS.md.

Не переносить целиком размер, дерево каталогов, Cobra, Factory, HTTP-слой или исторические решения GitHub CLI. Стандартная библиотека и один Go-модуль остаются исходным выбором. Обоснованное отступление от принятой рекомендации записать в docs/DECISIONS.md, когда этот файл появится; до этого — в журнале текущего этапа. Ссылаться на реальную причину, а не на личный вкус.

## Архитектура и организация файлов

- Разделяй пакеты по ответственности продукта: CLI, операции приложения, модель задач, Git-адаптер, хранение, tracking, hooks и импорт/экспорт. Схема и направления зависимостей — в SKILLS.md.
- Файл должен объединять понятную тему: start.go, completion.go, schema.go. Большой файл с несколькими независимыми сценариями разделять по этим сценариям. Не дробить один связный алгоритм на десятки файлов ради их размера.
- cmd/git-task/main.go содержит запуск и сборку зависимостей, но не бизнес-правила. Модель задач не знает о терминале, Git-процессах и файловой системе.
- Команды разбирают аргументы и отображают результат. Общая операция start/sync должна быть доступна CLI и hooks без копирования логики.
- Собирай зависимости явно в точке входа или выделенной функции сборки. Не вводи DI-контейнер, service locator или глобальную изменяемую конфигурацию.
- Интерфейс добавляй на стороне потребителя для конкретной границы или подмены в тесте. Интерфейс для каждого struct и пары X/XImpl не требуются.
- Не создавать пакеты utils/common/helpers как склад несвязанных функций. Помощник принадлежит пакету, смысл которого обслуживает.
- Не создавать заранее пустые пакеты, несколько go.mod, отдельные сервисы, универсальные CRUD-фреймворки или Repository/UseCase-обёртки по аналогии с Android. Новая абстракция должна решать текущую задачу.
- Go-имена — на английском; пояснения пользователю, план и проектные документы — на русском. Язык пользовательского CLI согласовать в SPEC и применять последовательно.

## Правила кода

- Форматирование — gofmt. Выбирай ясные имена, короткие имена пакетов и минимальную экспортируемую поверхность. Не скрывай смысл чрезмерными сокращениями.
- Ожидаемые ошибки возвращать как error. Добавлять полезный контекст; сохранять причину через %w, когда она нужна вызывающему коду. Проверять errors.Is/As, а не фрагменты Error().
- Не использовать panic/log.Fatal/os.Exit для обычных ошибок внутри пакетов. Окончательный код выхода формируется на границе приложения; очистка должна успеть выполниться.
- Ввод-вывод передавать через явные reader/writer или небольшую структуру. Библиотечные пакеты не печатают напрямую в глобальные stdout/stderr.
- Операции Git и другое отменяемое I/O принимают context.Context. Не использовать context как контейнер настроек и не добавлять его чистым функциям без причины.
- Ресурсы закрывать, ошибки значимых записей/закрытий учитывать. Не запускать goroutine без понятного владельца, отмены и ожидания завершения.
- Не добавлять комментарии в код, включая комментарии к API и в тестах. Инварианты, причины решений и границы Git-транзакций описывать в проектной документации. Это прямое указание пользователя имеет приоритет над рекомендациями о комментариях в SKILLS.md и внешних Go-руководствах. Существующие комментарии без отдельного запроса не удалять.
- Зависимости и версии фиксировать в go.mod/go.sum по необходимости. Не добавлять библиотеку ради одной простой функции и не отказываться от неё ценой собственной сложной инфраструктуры.

## Инварианты этого продукта

- Обычный start <branch> автоматически выбирает первый todo и создаёт ветку от target_branch. Явный выбор: --id по точному JSON id или --title по точному уникальному JSON title. Флаги взаимоисключающие; отсутствующий/неоднозначный title даёт ошибку, а не первый совпавший пункт. --select явно включает меню. Имя ветки обязательно во всех режимах; отсутствие имени, -b и лишние позиционные аргументы дают ошибку до мутаций/меню. Автогенерации нет, занятое имя даёт ошибку. Полный контракт — в PLAN.md.
- До первого done поле attempts отсутствует; текущая работа находится в active_attempt. Завершение одним обновлением переносит её в attempts и меняет статус на done. Обычный start для done даёт ошибку с --again; start с --id или --title и --again создаёт новую ветку/active_attempt и переводит done напрямую в active, сохраняя историю. Отдельной команды reopen нет. Ошибка создания ветки не меняет статус; повторный sync не дублирует завершение.
- План, настройки и задачи хранятся только в локальном .git-task/plan.json; init исключает /.git-task/ через Git info/exclude с сохранением чужих записей. Не создавать служебных веток/коммитов, отдельных config.json и tasks/<id>.json. Разрешены собственные локальные файлы данных/lock/журнала/резервной копии; файлы кода, .gitignore, индекс и история кода не меняются ради хранения. Не использовать скрытые reset, stash, force push или принудительное удаление ветки.
- Все вызовы Git идут через адаптер с отдельными аргументами. Проверять имена и границы опций; отсутствие shell не отменяет риск передачи нежелательных Git-опций.
- Различать «нет результата», «ошибка Git» и «операция уже произошла, но hook вернул ошибку». Повтор опасной операции должен опираться на фактическое состояние.
- Пустая ветка, удалённая ветка и старый достижимый коммит не являются самостоятельным доказательством завершения актуальной задачи.
- Локальные команды и hooks не ходят в сеть. Hooks не задают вопросов и не ломают чужие hooks. Перенос между компьютерами / remote sync (P13) и поддержка squash отложены за пределы первой версии; не реализовывать их без явного возобновления пользователем. Отрицательная проверка, что неподдерживаемое слияние не даёт ложного done, остаётся обязательной.
- Работа должна поддерживаться на Windows, Linux и macOS в заявленной матрице. Не обещать платформенную поддержку по одной успешной кросс-компиляции.
- Запись plan.json: валидация, межпроцессная блокировка, проверка прочитанной версии, безопасная замена и резервная копия последней валидной версии. Не затирать чужой/tracked-путь, повреждённый файл или обнаруженные внешние изменения. Прерванные операции диагностируются; прямой редактор не соблюдает блокировку CLI, поэтому нельзя обещать защиту от любой конкурентной правки. Подробности определяют SPEC и этапы хранения/tracking.

## Проверки перед передачей

Прямое требование пользователя: перед завершением задания написать все необходимые тесты и прогнать их. При изменении поведения добавь соответствующие позитивные, негативные и граничные сценарии; при исправлении ошибки — регрессионный тест, когда дефект воспроизводим. Не откладывай тесты до P15. Отформатируй затронутые файлы и выполни адресные проверки. После появления Go-модуля обязательный базовый набор перед готовой передачей изменения кода:

~~~text
go vet ./...
go test ./...
go build ./...
~~~

До появления модуля и для чисто документального изменения эти команды не являются обязательным ритуалом: проверяй документы и контракты. Race detector, fuzzing, govulncheck и межплатформенная матрица применяются по маршрутам SKILLS.md и критериям текущего этапа. Нельзя отмечать недоступную проверку как пройденную.

Если необходимые тесты падают или их невозможно запустить, не объявляй задание выполненным и не передавай этап как готовый в review. Исправь проблему в области задания либо зафиксируй незавершённость/блокер и точное следующее действие по PLAN.md. Записывай названия новых тестов, фактические команды и результаты. Проверяющий независимо запускает необходимые проверки перед принятием; одного отчёта исполнителя недостаточно.

Git-семантику проверять с настоящим Git во временных репозиториях. Подмены допустимы для вывода CLI и искусственных ошибок; одни mocks не доказывают правильность merge, refs и hooks.

Тесты не читают credentials и не меняют пользовательские Git-настройки. Интеграционное окружение задаёт собственные identity/config/hooks и использует изолированные каталоги. Не полагайся на наличие настроенного Git у автора теста.

## Работа с файлами и окружением

Работай внутри проекта и разрешённых пользователем мест. Сохраняй чужие изменения. Инструменты устанавливай локально в проект или разрешённый проектный каталог инструментов, не меняй глобальные настройки ради удобства. Не добавляй токены, ключи, реальные пользовательские пути и другие секреты в тестовые fixtures или отчёты.

Изменения в этих инструкциях должны быть связаны с текущим запросом пользователя или конкретным решением проекта. Не ослабляй проверки, чтобы принять неработающий этап. Внешний эталон не является разрешением изменять продукт, публиковать релиз или устанавливать инструменты глобально.

## Обязанности при ревью

Проверяющий оценивает и поведение, и устройство кода. Помимо критериев PLAN.md проверить:

- Можно ли быстро найти реализацию команды, её правила и тесты?
- Есть ли одна реализация общего сценария для CLI/hooks?
- Не смешаны ли в одном месте парсинг аргументов, Git-команды, сериализация и переходы задач?
- Обоснованы ли интерфейсы, новые пакеты, зависимости и конкурентность?
- Выполнены ли применимые правила выбранного Go-эталона?

Недостоверность, потеря данных и нарушения контрактов блокируют приёмку. Личные предпочтения по мелкому оформлению не должны блокировать работающий согласованный дизайн. Замечание по архитектуре должно содержать конкретную проблему связанности, тестируемости или понятности и минимальный способ её исправления.

Передача работы фиксируется в PLAN.md: что изменено, пути, команды и результаты, архитектурные решения, ограничения и следующее действие. Исполнитель не принимает собственный этап.
