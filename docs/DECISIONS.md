# Git Task — решения и допущения

Основа — [решения пользователя в PLAN.md](../PLAN.md). Ниже отделены их следствия от деталей, выбранных исполнителем P01. Эти детали входят в предлагаемую [SPEC.md](SPEC.md), но не являются отдельным подтверждением пользователя или приёмкой этапа. Прогресс и результат ревью хранятся только в PLAN.md.

## D01. Один локальный файл — подтверждённое требование

План, настройки и задачи находятся в `.git-task/plan.json`; локальный `info/exclude` содержит `/.git-task/`. Никаких служебных веток/коммитов, отдельного config или файла на задачу. Поэтому записи не зависят от Git identity, текущей ветки и staged-кода. Нужны собственные backup, lock, журнал и явный экспорт: обычные push/clone данные не переносят.

Факт Git: ignore не действует на tracked-файлы. Вывод продукта: init проверяет индекс/HEAD, а start/resume — также дерево назначения; нельзя исправлять конфликт скрытой правкой индекса. Источники просмотрены 2026-09-24: [gitignore](https://git-scm.com/docs/gitignore), [git rev-parse, --git-path и --show-toplevel](https://git-scm.com/docs/git-rev-parse).

## D02. Команды отделены от операций — подтверждённое направление

Один Go-модуль, исходно стандартная библиотека. CLI разбирает аргументы и выводит результат; общие start/sync координируются app; task хранит чистые правила, git вызывает процессы, storage отвечает за файлы, tracking — за доказательства, hooks — за события, transfer — за форматы. Зависимости передаются явно, интерфейсы появляются на стороне потребителя при конкретной потребности. Пустые пакеты и дополнительные слои заранее не создаются.

Это применение утверждённой архитектуры [SKILLS.md](../SKILLS.md), без переноса размеров, Cobra и Factory GitHub CLI. В P01 нет Go-кода и заимствования стороннего кода; отклонения от Go-эталона не вводятся. Исходники GitHub CLI для конкретной реализации пока не исследовались.

## D03. Start и история — подтверждённое требование

Имя ветки обязательно, обычный выбор — первый todo; --id/--title точные, title уникален по всему плану. --again работает с обоими селекторами только для done. Основание — локальная target_branch; --from меняет основание, не цель. Active_attempt хранит текущий подход, attempts появляется только при завершении. Старая история не доказывает новую работу. Нет reopen, --task, -b, автогенерации имени и force-семантики --again.

Дополнение P01: собственные сообщения CLI по-русски, как примеры PLAN; машинные имена по-английски. Коды выхода и обработка флагов определены SPEC §2. Это позволяет будущим этапам проверять единый CLI-контракт, включая флаги после branch.

## D04. Минимальная среда — допущение P01

Обычный репозиторий с единственным рабочим деревом и полной локальной историей. Bare, shallow, partial clone, linked worktree и основной репозиторий с дополнительными зарегистрированными worktree пока диагностируются без мутаций. PLAN прямо поручает определить эти границы P01/P14. Ограничение не заменяет обязательную матрицу Windows/Linux/macOS.

Причина: linked worktree разделяют часть Git-данных при разных рабочих каталогах; нельзя обещать один plan.json и уникальность связей без отдельной координации. Недостающая история также несовместима с безусловными доказательствами завершения. Источник о разделяемых данных: [git-worktree, REFS и DETAILS](https://git-scm.com/docs/git-worktree), просмотрен 2026-09-24. Это консервативный выбор продукта, а не утверждение, что Git не поддерживает эти режимы.

Unborn позволяет подготовить план, но не начать Git-подход до появления основания. Detached позволяет читать/редактировать план, но собственное переключение требует предварительно выбрать ветку. Start/resume отклоняют dirty tree; чистые операции плана его допускают. Init по умолчанию сохраняет main, не угадывая master; явный --target решает выбор. Эти ограничения не требуют сброса/очистки данных.

## D05. Жизненный цикл — допущение P01

Pause/resume сохраняют ID подхода. Paused продолжает наблюдаться: интеграция может произойти вне CLI. Archive замораживает незавершённый active_attempt, сохраняет историю, освобождает живую привязку и не удаляет ветку. Команды unarchive нет в первой версии; archived доступен для show/edit/move и полного экспорта. Это удовлетворяет сохранению истории без добавления незавершённого подхода в attempts.

Attach принимает todo и существующую локальную ветку, не переключает её. Rebind только явный для active/paused, сохраняет историю связи и не переносит автоматически доверие к старому tip. Complete разрешает ручной переход из todo/active/paused, подтверждается диалогом/--yes, необязательный --commit проверяется локально, source всегда manual. Повторные безопасные no-op перечислены в SPEC; новый start не становится идемпотентным созданием второй попытки.

## D06. Последнее завершение и хвост вставки — допущение P01

Хронология означает порядок зарегистрированных завершений. Монотонный номер события под блокировкой надёжнее часов commit/компьютера и сохраняется в JSON. Если sync впервые обнаруживает несколько завершений без достоверного порядка, назначает события в порядке плана. Markdown [x] без дат обрабатываются в порядке строк, последняя [x] становится опорой. Фактическая дата завершения остаётся неизвестной.

Сохраняемый хвост группы позволяет add X, затем add Y получить X,Y, а не Y,X. Импорт без завершений сам образует начальную группу; последующий add идёт в её конец. Новое завершение меняет только будущую опору. Явные размещения хвост не меняют; move самого хвоста переносит будущую точку вставки вместе с его ID. Archive/--again не стирают прошлое завершение. Примеры в SPEC §6 являются нормативными, для P04 нужны тесты последовательностей.

## D07. Завершение требует доказательств текущей попытки

Факты Git: --is-ancestor различает истину (0), ложь (1) и ошибку (другие коды); squash не записывает обычную merge-связь. Источники просмотрены 2026-09-24: [git-merge-base](https://git-scm.com/docs/git-merge-base), [git-merge](https://git-scm.com/docs/git-merge).

Вывод продукта: нельзя завершать только по ancestry сохранённого SHA. Нужны наблюдавшаяся работа вне цели, актуальность tip/связи и доказанная интеграция текущего подхода. Пустая ветка и обновление из main не доказывают работу. Старое достижимое наблюдение при новых commit, исчезновении или пересоздании ветки не доказывает актуальное состояние. При недостатке данных — неопределённость, не done. После пропуска только merge-hook локальная сверка должна восстановить результат по оставшимся доказательствам.

P09 обязан конкретизировать достаточные наблюдения в TRACKING.md и проверить реальные графы. SPEC намеренно не объявляет один ancestry-запрос готовым алгоритмом. Произвольное внешнее удаление/пересоздание без следов не всегда наблюдаемо; это предел локального аудита, не разрешение использовать известные устаревшие данные.

## D08. Git и JSON не являются одной транзакцией

Сначала намерение, затем Git, затем запись связи. Журнал содержит исходный статус/историю и идентичность операции. Нельзя считать любой ненулевой код Git отсутствием результата: post-checkout выполняется после изменения рабочей копии и может повлиять на код команды. Источник просмотрен 2026-09-24: [githooks, post-checkout](https://git-scm.com/docs/githooks).

Восстановление проверяет факты и никогда не удаляет ветку для автоматического отката. Backup не заменяет plan.json при обычном чтении. Init также имеет два отдельных файловых эффекта (exclude и план); порядок и повтор должны быть безопасными. Никаких обещаний абсолютной защиты от сбоя питания или внешнего редактора между последней проверкой содержимого и заменой файла. Платформенные гарантии обосновываются реализацией P05, не предположением об одинаковом rename.

Уточнение по P01-R01: успешная замена plan.json может предшествовать закрытию журнала. До неё в журнале сохраняется доказательство подготовленного результата, связанное с ID операции: ожидаемая ревизия и содержимое/отпечаток всего плана; отдельно остаётся исходный снимок. Recovery различает исходный план, уже применённый собственный результат и постороннюю/неопределённую правку. В первом случае можно дописать результат при подтверждённом Git-эффекте; во втором — только закрыть журнал без Git и записи плана; в третьем — отказ с сохранением данных. Нельзя применять к уже записанному результату требование неизменности исходной задачи. Сравнения только active_attempt недостаточно, особенно для resume, который сохраняет ID подхода. Точный формат доказательства остаётся P05/P06.

## D09. Импорт, экспорт и редактор — допущение P01

Markdown — строго плоский чеклист с необязательными пустыми строками/ATX-заголовками. Прочие конструкции дают ошибку с номером строки. Это проще проверить, чем молчаливо игнорировать потерянные пункты. Markdown-экспорт — читаемое представление с явным предупреждением о потерях, JSON — полный снимок. В непустой план импорт не применяется; --yes не обходит защиту. JSON сохраняет настройки и порядок, но не создаёт ветки/hooks и не переносит доверие к наблюдениям без проверки.

Отдельного note нет: description решает текущую потребность. Edit предлагает полевые флаги и временный документ только title/description; ID/история не передаются редактору как изменяемые поля этой команды. Выбор редактора и конфликт версии определены в SPEC. Конкретное кроссплатформенное исполнение конфигурации редактора проверяет P11.

## D10. Hooks и диагностика — допущение P01

Init не устанавливает hooks: интеграция включается отдельной командой. Простая локальная цепочка сохраняет обычный чужой hook; неизвестные менеджеры и общий hooksPath требуют ручного подключения, без перезаписи. Uninstall не удаляет изменённые пользователем обёртки и данные плана. Собственная ошибка tracking не меняет результат чужого hook.

Doctor по умолчанию только диагностирует. Repair-операции названы в SPEC, требуют предпросмотра и подтверждения, --yes отменяет только вопрос. Возраст lock не доказывает смерть процесса. Незавершённый журнал блокирует новые мутации до разбора, status остаётся читаемым. Это позволяет явно сообщать о частичном эффекте, не выдавая опасный повтор за исправление.

Recover-start снимает блокировку после подтверждённого уже сохранённого результата, завершая только обслуживание своего журнала. Это не новая операция запуска: задача, подход, attempts, ревизия и backup не меняются. Сбой самого repair после записи обрабатывается той же ветвью при повторе; сбой закрытия журнала не откатывает сохранённый план. После успешного закрытия повтор repair без журнала — no-op с кодом 0 без вопроса. При последующей чужой правке либо недоказанном результате отказ сохраняется. Сопоставление и закрытие выполняются с проверкой версии и ID журнала под блокировкой после диалога; чужое намерение не удаляется.

## D11. База каркаса P02

Локальный модуль называется `git-task`, без вымышленного GitHub-адреса. Выбраны
Go 1.26 (поддерживаемая на момент выбора ветка инструментария) и базовый Git 2.51.
Код использует стандартную библиотеку, `exec.CommandContext`/`WaitDelay`,
`rev-parse --path-format=absolute` и `GIT_NO_LAZY_FETCH`; более старые версии не
заявлены. Это консервативная база для последующей матрицы, а не утверждение,
что все эти возможности впервые появились именно в указанных версиях.
Точные фактически запущенные версии и результаты находятся в журнале PLAN.

Каркас ограничен help/version и адаптером; Git не проверяется на старте CLI,
чтобы справка работала без установленного Git. `git.New` сообщает об отсутствии
Git, а ошибки процесса не превращаются в отрицательные ответы автоматически.
Нереализованные команды отказывают, а не имитируют успех; doctor пока не вводит
частичную диагностику вместо будущего контракта P14. Валидация имени ветки
получает буквальный полный ref, без расширения `@{-1}`.

Проверено по первоисточникам 2026-09-25:
[Google Go Style Guide](https://google.github.io/styleguide/go/guide),
[Go Code Review Comments](https://go.dev/wiki/CodeReviewComments),
[структура модуля](https://go.dev/doc/modules/layout),
[описание устройства GitHub CLI](https://github.com/cli/cli/blob/trunk/docs/project-layout.md),
[os/exec](https://pkg.go.dev/os/exec),
[rev-parse](https://git-scm.com/docs/git-rev-parse),
[окружение Git](https://git-scm.com/docs/git),
[merge-base](https://git-scm.com/docs/git-merge-base).
У GitHub CLI использовано описание разделения обязанностей; исходники команд
не копировались и не служили нетривиальным образцом. Отступлений от принятых
Go-принципов нет. Установка инструментов, кеши и сборки локальны проекту;
инструкции воспроизведения — [DEVELOPMENT.md](DEVELOPMENT.md).

## D12. Модель и формат P03

Доменные данные и чистые переходы собраны в `internal/task`, без интерфейсов,
новых зависимостей, часов процесса или файлового I/O. Формат схемы 1 и контракты
методов описаны в [MODEL.md](MODEL.md). ID задаёт вызывающая операция; проверка
уникальности не зависит от времени. Выдача новых задач/номеров относится к P04,
ID Git-подхода сохраняется в намерении P06 до внешнего эффекта.

У активного и завершённого подхода общий тип, но completion допустим только
в истории. Это позволяет переносить один и тот же подход без потери исходной
ветки/перепривязок. Переходы работают с копией затронутой задачи и присваивают
план только после полной валидации. No-op не меняет ревизий. Такая атомарность
касается памяти одного процесса; протокол диска остаётся обязанностью P05.

JSON намеренно строгий: неизвестные поля, дубликаты ключей и null отклоняются,
чтобы чтение с последующей записью не теряло чужие данные молча. Методы JSON
расположены отдельно от переходов и не работают с файлами. Счётчик завершений
задаёт зарегистрированный порядок; времена могут совпадать или идти назад.
Merge-доказательства проверяются структурно; алгоритм доказательства остаётся P09.

Применены ясные конкретные типы и минимальная экспортируемая поверхность;
отступлений от принятых Go-принципов нет. Повторно просмотрены 2026-09-27:
[Google Go Style Guide](https://google.github.io/styleguide/go/guide),
[Go Code Review Comments](https://go.dev/wiki/CodeReviewComments),
[структура модуля](https://go.dev/doc/modules/layout).

Дополнение по P03-R01/R02: стандартный JSON-декодер заменяет непарные
UTF-16-суррогаты, поэтому перед декодированием проверяются исходные escape
в синтаксически корректном JSON. Проверка не запрещает настоящий U+FFFD.
Исходные смещения дат проверяются отдельно от time.Parse, который может
нормализовать недопустимые минуты. Даты, переданные через Go API, проходят
ту же проверку диапазона смещения; секундные смещения отклоняются, поскольку
формат RFC3339 их не сохраняет. Это сохраняет гарантию отказа без изменения
плана и не требует собственных типов времени или полного JSON-парсера.

## D13. Операции порядка и локальная выдача идентификаторов

Add/Edit/Move — методы существующего `internal/task`; Git, часы, файловое I/O,
интерфейсы и новые зависимости им не нужны. Position задаёт before/after/end,
нулевое значение — автоматическое добавление. EditOptions использует указатели
для различения пропущенного поля и очистки description. Ошибки и no-op сохраняют
ревизии; Move работает с независимой копией order, чтобы не менять исходный
план при последующей ошибке. История отделена от порядка отображения.

Add выдаёт `task-NNN`/`T-NNN` из максимума сохранённых числовых суффиксов обоих
полей; точные правила и границы — в [MODEL.md](MODEL.md). Все задачи сохраняются,
включая archived, поэтому отдельный счётчик и изменение схемы сейчас не нужны.
Это уточняет отложенную в D12 выдачу ID задачи; ID подхода по-прежнему задаёт
вызывающая операция. Выдача локальна для одного плана, соответствует отложенному
P13 и требует общей блокировки хранилища при появлении записи на диск в P05.
Произвольный внешний редактор способен изменить идентификаторы: защиты от такой
перезаписи истории этот алгоритм не обещает.

Новая ревизия задачи после Add равна 1. Реальный Move увеличивает также ревизию
перемещённой задачи; переставленные соседи не изменяются. Повтор того же порядка
не является изменением. У импортируемого Markdown сначала создаются все todo в
порядке строк, затем регистрируются отмеченные завершения в том же порядке:
это использует существующие доменные операции и сохраняет правило SPEC §6.

Отступлений от Go-эталонов нет; 2026-09-27 повторно просмотрены
[Google Go Style Guide](https://google.github.io/styleguide/go/guide),
[Go Code Review Comments](https://go.dev/wiki/CodeReviewComments) и
[структура модуля](https://go.dev/doc/modules/layout).

## D14. Канонический статус active

По прямому решению пользователя от 2026-09-27 выполняемая задача называется
`active`. Переименованы JSON-значение, Go-константа `task.Active`, переходы,
тесты, SPEC, ACCEPTANCE, MODEL и правила/журнал PLAN. По просьбе пользователя
название обновлено и в исторических описаниях; факты приёмки этапов сохранены.
Алиас прежнего значения не принимается, что проверяется отрицательным тестом.
Версия схемы остаётся 1: первая версия продукта ещё не выпущена; произвольные
локальные пользовательские файлы не переписываются автоматически.

## D15. Снимок, межпроцессная блокировка и безопасная запись

Протокол до реализации зафиксирован в [STORAGE.md](STORAGE.md).
Storage получает готовые абсолютные пути и потребительский интерфейс Guard с
двумя проверками Git; сам не строит Git-команды. Приложение связывает чтение,
доменную операцию и Save в `internal/app`. Этот пакет появился уже в P05,
поскольку подключение init/add/status требует координации трёх существующих
ответственностей; помещать файловую транзакцию в CLI означало бы смешать их.

Снимок сохраняет исходные байты отдельно от редактируемой модели. Save берёт
эксклюзивный write.lock, проверяет исходник и валидирует результат. Add может
подготовить номер вне блокировки, но записывает его только после проверки
снимка под блокировкой; устаревшая операция получает конфликт, поэтому два
процесса не могут успешно сохранить один и тот же номер поверх друг друга.
Автоматического повтора Add после неясного результата нет.

Использованы O_EXCL для блокировки, синхронизация и закрытие временного файла,
резервная копия исходных валидных байтов и os.Rename в одном каталоге. Для
первого создания используется os.Link: существующий файл не заменяется даже
при внешнем появлении между проверкой и публикацией. Файловая система без
hard links получает диагностический отказ с сохранением подготовленного файла.
Защита от отключения питания и любого внешнего редактора не обещается.
Директории/ссылки по служебным путям и повреждённый backup отклоняются.

Остаток write.lock или pending-файла требует разбора, а не автоматического
удаления. Возраст lock не доказывает отсутствие владельца. Полный интерфейс
восстановления doctor остаётся P14. Реальных старых схем для миграции пока нет;
диспетчер версии отказывает на неизвестной схеме без потери данных.

Стандартная библиотека; новые внешние зависимости и production-goroutine не
добавлены. Тесты используют настоящий Git и дочерние тестовые процессы,
синхронизируемые каналами stdin/stdout, без sleep и пользовательской identity.
При подготовке просмотрены 2026-09-27 [os.Rename](https://pkg.go.dev/os#Rename),
[git-worktree](https://git-scm.com/docs/git-worktree),
[git-check-ignore](https://git-scm.com/docs/git-check-ignore) и принятые Go-эталоны.

Дополнение к D15 после P05-R01 (2026-09-28): Git хранит написание пути, которое
может отличаться от имени `.git-task` только регистром. Индекс запрашивается
через `:(top,icase,literal).git-task`, HEAD — через список корневых имён
`ls-tree --full-tree --name-only -z` (эта команда не поддерживает icase).
Найденные варианты проверяются по файловой идентичности через `os.SameFile`;
при отсутствии обоих вариантов используется проверка поиска существующих
имён в родительском каталоге без записи. Безусловное приведение к нижнему
регистру отвергнуто: оно запрещало бы независимый каталог на Linux. Проверка
применяется до мутаций Init/Load/Save; ошибка определения свойств пути означает
отказ. Просмотрены [Git pathspec](https://git-scm.com/docs/gitglossary#Documentation/gitglossary.txt-icase)
и [os.SameFile](https://pkg.go.dev/os#SameFile).

## D16 — Журнал запуска и подтверждение владения веткой

P06 использует общую блокировку хранения, исходные байты всего плана и полный
подготовленный результат в `operation.json`. SHA-256 выявляет повреждение
журнала; сравнение исходных байтов обнаруживает внешнюю правку, включая пробелы.
Уже записанный собственный результат отличается от посторонней правки без
повторной записи plan.json/backup. Протокол описан в [START.md](START.md).

Создание ref и checkout разделены: `update-ref --no-deref --create-reflog`
с ожидаемым нулевым старым ID отказывает при гонке создания. Уникальный ID
операции в reflog позволяет подтвердить владение после прерывания. Затем
`checkout --no-overwrite-ignore` защищает игнорируемые файлы. После Git всегда
проверяются фактические ref/HEAD; ненулевой post-checkout не отменяет уже
совершённый запуск. Ветку не удаляем для отката. Между созданием и checkout
есть явно диагностируемая граница: recovery не переключает HEAD самостоятельно.

Это усложнение требуется для отличия собственной операции от совпавшей чужой
ветки. Не вводятся служебные ветки, коммиты данных, зависимости или фоновые
процессы. Поле ID попытки уже существует в модели; формат плана не меняется.
Просмотрены 2026-09-28: [update-ref](https://git-scm.com/docs/git-update-ref),
[checkout](https://git-scm.com/docs/git-checkout), применимые руководства
[Google Go Style](https://google.github.io/styleguide/go/guide),
[Go Code Review Comments](https://go.dev/wiki/CodeReviewComments) и
[Organizing a Go module](https://go.dev/doc/modules/layout).

## D17 — Меню как подготовка общей операции start

P07 вводит `PrepareSelection` и непрозрачный снимок для `StartOptions`.
Снимок включает точные байты плана, основание и HEAD. Сравнение под существующей
блокировкой происходит до доменного перехода и записи журнала. Проверяется
весь план: это сохраняет выбор по ID и контекст порядка/названий, который
пользователь видел. Изменившийся план требует нового явного запуска меню.
Никакой lock не удерживается при ожидании ввода. Схема JSON не меняется.

Граница CLI — небольшой Dialogue с ReadLine(context) и Close; фабрика
передаётся вместе с потоками. Обычный start не открывает Dialogue. Реальная
фабрика проверяет stdin и stderr средствами ОС; файлы, pipe и NUL не считаются
терминалами. Полноэкранный интерфейс и смена режима терминала не нужны.

Linux/macOS открывают собственный неблокирующий дескриптор /dev/tty; отмена
контекста ставит deadline чтению. Callback отмены завершается до закрытия
дескриптора. На Windows используется небольшой последовательный цикл чтения
INPUT_RECORD через ReadConsoleInputExW с CONSOLE_READ_NOWAIT, с ожиданием до
25 мс и проверкой контекста. Проверка доступности API возвращает обычную ошибку
при неподдерживаемой среде. Нет гонки между проверкой числа событий и
блокирующим чтением, если Ctrl+C очистил буфер. Цикл
обрабатывает Unicode, повтор клавиши, Backspace, Enter и отмену; продвинутое
редактирование строки не входит в этот интерфейс. Блокирующее ReadConsole
ожидает Enter и усложняет гарантированное завершение по context. Отдельная
горутина чтения и изменение консольного режима не требуются. Зависимости не
добавлены: используемые системные границы малы и проверяются настоящими PTY
на Linux и отдельной скрытой консолью Windows. Проверка macOS остаётся в
платформенной матрице P15/P17.

Просмотрены 2026-09-29: [os.File.SetReadDeadline](https://pkg.go.dev/os#File.SetReadDeadline),
[ReadConsole](https://learn.microsoft.com/en-us/windows/console/readconsole),
[ReadConsoleInput](https://learn.microsoft.com/en-us/windows/console/readconsoleinput),
[ReadConsoleInputEx](https://learn.microsoft.com/en-us/windows/console/readconsoleinputex),
[INPUT_RECORD](https://learn.microsoft.com/en-us/windows/console/input-record-str),
[KEY_EVENT_RECORD](https://learn.microsoft.com/en-us/windows/console/key-event-record-str).

## D18 — Подготовленный импорт и точный JSON-снимок

P08 добавляет небольшой `internal/transfer`: чистые функции форматов используют
существующие операции и строгий JSON модели. Markdown сначала создаёт весь
порядок todo, затем регистрирует imported-завершения по порядку строк.
Даты импорта и завершения не назначаются: неизвестные поля отсутствуют.
Предпросмотр и диалог принадлежат CLI; применение снимка — app/storage.

Подготовленный импорт хранит исходные байты назначения и приватные канонические
байты результата. Изменение публичной модели предпросмотра не подменяет запись.
Блокировка не удерживается во время диалога. App повторяет чтение и сравнение,
storage повторяет проверку под lock, не допускает импорт в непустой план.
Новая `Store.Import` использует общий путь Save с единственным отличием:
в пустом назначении сохраняется revision JSON без увеличения, даже 0.
Обычный Save сохраняет прежнее требование монотонности revision.

Export читает согласованный снимок без sync и отказывает при pending/lock/журнале.
Файл публикуется через временный файл, Sync/Close и os.Link: существующий путь
не заменяется, в том числе если появился между проверкой и публикацией.
Каталоги метаданных защищены проверкой файловой идентичности родителя и предков,
а не только текстовым сравнением путей. Гарантии и ограничения —
[TRANSFER.md](TRANSFER.md). Внешние зависимости, новые фоновые процессы,
схема хранения и транспорт P13 не добавлены.

Просмотрены 2026-09-30 [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments)
и [структура модуля](https://go.dev/doc/modules/layout). Повторное открытие
Google Go Style Guide через web-инструмент вернуло restricted URL;
применены зафиксированные правила AGENTS.md/SKILLS.md, успешное чтение этого
внешнего источника в данной сессии не заявляется. Отступлений от применимых
правил нет; запрет новых комментариев в коде следует прямому указанию пользователя.
