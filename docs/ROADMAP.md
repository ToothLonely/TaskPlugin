# Дальнейшие задания

Требования и прогресс имеют один источник — [PLAN.md](../PLAN.md).
Этот документ раскрывает задания после первой версии, не отмечает их выполненными
и не разрешает начать реализацию автоматически. Очередь TODO-01–04 сохранена.
Владелец продуктовых решений — пользователь; исполнитель готовит предложение
и реализацию по отдельному запросу, независимый проверяющий подтверждает результат.
Текущая передача и команды финальной проверки — [HANDOFF.md](HANDOFF.md).

## TODO-01. Подтверждение изменений через remote

Сейчас разрешена offline-работа. Обычный push и квитанции устойчивых действий
позволяют повторить доставку после потерянного ответа, но не дают обязательного
серверного readback. Done учитывает только известные подходы; поздний подход
может снова открыть задачу.

Следующее задание: подготовить решение о повторном получении серверной версии
после публикации и проверке ID/полей задачи, подхода и действия. Отдельно выбрать,
нужна ли обязательная онлайн-регистрация перед успешным началом работы и как
она сочетается с offline, отменой и уже совершившимся checkout. Проверка интерфейса
хостинга требует выбора конкретного provider и отдельного доступа.

Владелец решения — пользователь. Исполнитель сначала фиксирует контракт успеха,
отказа и совместимости. Проверяющий проверяет потерянный ответ, изменение remote
между push/readback, недоступность сети, повторы без новых ID и позднюю доставку.
Не обещать отсутствие неизвестных подходов до принятия нового режима регистрации.

## TODO-02. Права ручного редактирования

Сейчас author сообщает происхождение записи из Git identity. Он не удостоверяет
личность и не ограничивает ручной push плана. Локальная проверка CLI не является ACL.

Следующее задание после TODO-01: согласовать роли и разрешённые действия — кто
редактирует описание, порядок и назначение задач, кто изменяет подходы. Выбрать
серверную проверку идентичности/прав и поведение старых данных без author.
Владелец политики — пользователь; администратор выбранного сервера отвечает
за доступ и настройку, исполнитель — за реализацию согласованного механизма.
Проверяющий проверяет обход CLI прямым push, подмену author, отказ прав и сохранность
локальной очереди. До серверной проверки не заявлять защищённые роли.

## TODO-03. Конфликты ручных изменений

Сейчас несовместимость диагностируется, обе стороны и неопубликованные действия
сохраняются. Универсального автоматического или интерактивного resolver нет.

Следующее задание после решения о правах: определить допустимые автоматические
правила, явный выбор человека и аудит решения для следующих случаев:

- Два title: «Добавить вход» и «Добавить регистрацию».
- Один переместил пункт в начало, другой — в конец.
- Один удалил/архивировал задачу, другой начал подход.
- Две разные задачи получили одинаковый старый последовательный ID/номер.

Владелец семантики — пользователь. Исполнитель готовит формат сохраняемого
конфликта и порядок применения решения; проверяющий проверяет оба порядка
доставки, повтор решения, сохранность attempts/очереди и отсутствие молчаливой
перезаписи. Не менять устойчивые ID существующей истории ради удобства resolver.

## TODO-04. Среды и платформенная матрица

По решению пользователя 2026-10-05 остаток P17-B01 отложен отдельным заданием:
native Linux/macOS amd64 Checks/Race на Go 1.26.0/1.26.8 и Git 2.51.0,
Windows `TestSymlinkStoragePreservesDestination` и
`TestReleaseOutputDirectory/symlink` на обеих Go без SKIP. Эти результаты
не подтверждены. Docker daemon и macOS runner не предоставлены; junction
не заменяет symlink. Отложенные случаи не блокируют P18 по этому решению.

Владелец доступа и разрешения внешнего запуска — пользователь. Исполнитель
готовит native runner, точный кандидат/manifest и команды; проверяющий запускает
их и сохраняет реальные логи. Для неизменённого R02 маршрут описан в
[RELEASE-ACCEPTANCE.md](RELEASE-ACCEPTANCE.md). Архивы находятся в игнорируемой
`.tools/releases/0.1.0-rc.1-r02` и не появятся от одного checkout.
Текущий checks.yml и Docker-драйвер обслуживают P15/P18; отдельный маршрут P17
надо подготовить, например для ubuntu-24.04 и macOS Intel. Конфигурация workflow
сама по себе не доказывает исполнение.

Если продукт изменён, выбрать новый окончательный кандидат и заново привязать
проверки к его hash; прежние результаты R02 ему не принадлежат. SKIP, отсутствие
runner и кросс-компиляция не заменяют PASS. Полный прогон будущего кандидата
согласовать в отдельном задании, сохранив доказательства P18.

## Остальные расширения

Они не меняют порядок TODO-01–04 и требуют самостоятельного запроса пользователя.

| Задание | Решение и граница будущей работы |
|---|---|
| Squash и переписанная история | Пользователь выбирает допустимые доказательства. Сейчас squash/cherry-pick не дают автоматический done; обязательны отрицательные проверки ложного завершения перед добавлением поддержки. |
| Расширение переноса | Выбрать формат и перенос веток/коммитов кода, одинаковые имена, локальные связи и очередь. Сейчас JSON переносит общий снимок, не offline-очередь, не Git-объекты и не настройку remote. Перенос веток кода не является незавершённым требованием P13. |
| Интеграция хостинга | Выбрать SaaS/provider, триггер, identity/права и повтор после отказа. Сейчас есть пример post-receive с полным clone-worker на управляемом сервере; внешнего deployment и готового универсального SaaS-задания нет. |
| Доставка и рост истории | При необходимости выбрать планировщик повторов, мониторинг и компактизацию actions. Сейчас нет фонового сервиса; очередь доставляется явным publish или разрешённой мутацией. |
| Публикация выпуска | Пользователь выбирает лицензию, канал распространения, версию и разрешает публикацию отдельно. Локальный кандидат и его checksum не являются опубликованным релизом. |

Принятая публикация использует ограниченный optimistic retry с обычным push.
Общая серверная блокировка и единственный публикующий обработчик не являются
недоделками первой версии. Менять этот алгоритм следует только для конкретного
нового требования, сохранив проверенные свойства очереди и повторов.
