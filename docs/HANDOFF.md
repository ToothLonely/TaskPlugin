# Передача окончательного кандидата

Прогресс, результаты и решение о приёмке записываются только в
[PLAN.md](../PLAN.md). Этот документ — карта продукта и инструкция проверяющему,
без утверждения о прохождении финальных тестов. Дальнейшие задания и владельцы
решений — [ROADMAP.md](ROADMAP.md). Публикация релиза требует отдельного запроса.

## Что передаётся

Личный режим хранит один игнорируемый `.git-task/plan.json`. Start создаёт ветку
от target, обычный merge/fast-forward завершает только доказанный подход,
ручное завершение явно имеет источник manual. Общий режим включается через
`team connect --remote <name>`: отдельная git-task-plan того же remote содержит
только метаданные, не вливается в код и не требует переключения рабочего дерева.

Действует схема 2: все attempts имеют устойчивые ID и status, новые записи —
author из Git identity. Done требует непустого набора всех известных done.
Поздняя offline-доставка может вернуть active. Author не является ACL,
неизвестный автор старой истории не выдумывается. Миграция схемы 1 явная,
сохраняет ID, историю, исходные байты и backup. JSON transfer исключает локальные
настройки, наблюдения и очередь; экспорт не заменяет резервную копию offline-работы.

Пакеты `cli`/`hooks` обращаются к общим операциям `app`; модель `task` не
зависит от терминала, Git и файлов. `git` выполняет процессы с отдельными
аргументами, `storage` отвечает за запись, `tracking` — за доказательства,
`transfer` — за форматы. Сборка зависимостей находится в `cmd/git-task`.

## Алгоритм публикации и его пределы

Реализация — `internal/app/team.go`, детали — P13-IMPLEMENTATION.
Получить свежую служебную базу, согласовать её с локальными действиями по ID,
валидировать, создать metadata commit и обычный fast-forward push. Сеть идёт
вне storage-lock; после сети перепроверяется локальный снимок. Устаревший push
при гонке повторяется с новой базой: максимум три цикла за общий срок 30 секунд.
Нет force push, текстового merge JSON или общей серверной блокировки.

Неудача оставляет очередь с прежними action/attempt ID. Квитанции позволяют
при повторе распознать уже опубликованное действие после потерянного ответа;
не надо повторять start/add/complete ради доставки. Успех локальной мутации
с предупреждением о публикации может иметь код 0; явный `team publish` при
отказе имеет ненулевой код. Push acknowledgement не обещает сильный readback.

Независимые адресные проверки P13/P15/P17 в PLAN подтверждали локальный file
transport, гонки до успеха третьей попытки, исчерпание лимита с последующей
доставкой, потерянный ответ, отмену и отсутствие дублей. Это не доказательство
HTTPS/SSH-provider, произвольного количества гонок или всех сетевых отказов.
Финальные результаты полного набора P18 для точного дерева записываются в PLAN.

Status/sync/hooks не ходят в сеть. Reference hook применяет уже полученную
служебную ссылку; fetch/pull требует подходящего refspec и сам не публикует
очередь. Серверный post-receive с полным clone-worker проверяет before/after
target и сохраняет событие/очередь перед публикацией. При отказе самой первой
записи событие не гарантированно сохранено: журнал сервера содержит команду
повторения с OID. Ветка подхода должна оставаться доступной до обработки.
Администратор сервера обеспечивает worker, права и повтор; универсальной
SaaS-интеграции, фонового повторителя и запуска после появления сети нет.

## Восстановление

Сначала `git task doctor` и проверка фактических ветки/HEAD/очереди: ненулевой
код hook не означает отсутствия Git-эффекта. Repair выбирать по диагнозу —
`recover-start`, `restore-backup`, `unlock`; `--yes` не отменяет проверок.
Recover-start распознаёт уже записанный результат и не создаёт второй подход.
Restore-backup может отбросить более свежую очередь; повреждённый оригинал
сохраняется для разбора. Возраст lock не доказывает отсутствие владельца.
После восстановления связи/сети — `git task team publish` с прежними ID.

Не удалять plan/journal/queue и не затирать сторону конфликта. Backup сохраняет
последнюю валидную версию, прямой редактор не соблюдает блокировку CLI. При
неоднозначном журнале остановить мутации и передать данные на явный разбор.
Uninstall сохраняет план, очередь, служебную историю и чужие hooks.

## Точное дерево и независимый финальный прогон

База ветки `feat/p18-handoff` — локальный master `ef3dc87`; продукт P18 не меняет.
Окончательный кандидат проверки — эта база плюс текущие документальные изменения
и тесты, принятые P17. Перед запуском сохранить `git rev-parse HEAD`,
`git status --short`, diff и SHA-256 входов. Исполнитель оставляет локальный
снимок `.tools/p18-handoff/input-hashes.json` и `input.diff`; они игнорируются
Git, при переносе передаются отдельно либо создаётся новый снимок дерева.
Проверяющий сверяет снимок перед запуском и после, записывает результаты в PLAN.
Если меняются Go-код/тесты/драйвер, прежний результат финального набора не применим.

R02 версии `0.1.0-rc.1` находится в `.tools/releases/0.1.0-rc.1-r02`.
Manifest SHA-256 `1d2feeb2d0a45fcbdf0b9e2e214bf5ced4fb611bfc83c695e2b085680dbb0657`;
архивы/hash описаны в RELEASE-ACCEPTANCE. Это упаковка P16 со старыми документами,
не архив обновлённой передачи P18. Не выдавать его source hash за hash текущего
дерева. Переупаковка/публикация для документальной передачи не выполнялась.

| Windows/amd64 | 1.26.8 | 2.51.0.windows.1 | Checks: vet, полный test без кеша, build |

Запускать последовательно, из корня проекта, отдельными процессами PowerShell.
Сохранять stdout/stderr и exit code; ошибка любой команды блокирует приёмку.

```powershell
powershell -NoProfile -File scripts/check.ps1 -Stage P18 -Mode Checks -Go .tools/review-go-min/go/bin/go.exe
powershell -NoProfile -File scripts/check.ps1 -Stage P18 -Mode Checks -Go .tools/go/bin/go.exe
```

Драйвер выполняет `go vet ./...`, `go test -count=1 -timeout=60m ./...`,
`go build ./...`. У P18 нет `-run`: исполняется весь проект, включая scripts.
Он очищает P17 candidate-переменные: cmd-тесты собирают бинарник из проверяемых
исходников. `-CandidateDirectory` не переключает P18 на архив R02.
Проверяющий отдельно сверяет неизменность продуктового кода относительно P17.
Драйвер задаёт изоляцию Git, только file transport, локальные кеши/temp и
отключает загрузку Go-модулей. Пользовательские credentials не нужны.

Дополнительные финальные маршруты доступной Windows-среды: выбранные race из
p15-tests.json (app/storage), четыре fuzz-target по 30s, security с подготовленным
govulncheck. Race требует CGO/C-компилятора; пути/окружение взять из фактической
доступной среды проверяющего, не устанавливать глобальные инструменты.

```powershell
powershell -NoProfile -File scripts/check.ps1 -Stage P18 -Mode Race -Go .tools/go/bin/go.exe
powershell -NoProfile -File scripts/check.ps1 -Stage P18 -Mode Fuzz -FuzzTime 30s -Go .tools/go/bin/go.exe
powershell -NoProfile -File scripts/check.ps1 -Stage P18 -Mode Security -Go .tools/go/bin/go.exe -Govulncheck .tools/review-bin/govulncheck.exe
```

Лимит полного тестового пакета увеличен с 20 до 60 минут по разрешению
пользователя после прогона, в котором cmd/git-task и internal/app не успели
завершиться за 20 минут. Это общий лимит каждого пакета, а не отдельного теста;
он даёт запас для полного Windows-набора с настоящим Git. Общий срок CLI/hooks
тестового репозитория увеличен с 3 до 10 минут: длинный offline-сценарий
под нагрузкой полного набора достигал прежней границы. Ошибка тестового CLI
показывает состояние context, чтобы различать истечение тестового срока и
отказ команды. Продуктовые сроки
операций, включая 30 секунд публикации, и проверки поведения не изменены.

Security обращается к публичной базе Go; offline-снимок требует указания
даты/источника через `-VulnerabilityDatabase`. Проверяющий сохраняет результат,
оценивает достижимость находок и фиксирует недоступность необходимой проверки
как блокер, без выдуманного PASS. Тайм-аут полного набора — FAIL: диагностировать
причину и согласовать корректный повтор всего набора, не заменить его фильтром.

Для каждого запуска записать ОС/архитектуру/файловую систему, Go/Git/CC,
SHA/dirty diff/hash входов, команду, код выхода и логи. Разобрать все SKIP:
платформенные пропуски на другой ОС ожидаемы, Windows symlink остаётся TODO-04
и не считается PASS. Native Linux/macOS Checks/Race также отложены TODO-04;
это согласованное исключение, не подтверждённая поддержка.

Для продолжения работы читать текущее состояние и последнее решение в PLAN.
При проверке нового кандидата сопоставить документы и критерии, выполнить
необходимые маршруты и сохранить факты в журнале соответствующего этапа.
Приёмка, коммит и локальное слияние выполняются по протоколу PLAN;
прежние результаты не подтверждают изменённый код.
