# Локальные Git-hooks

> Уточнение 2026-10-04: ниже описана принятая реализация P01–P12 со схемой 1. Целевой контракт P13 с несколькими attempts, author, общей веткой git-task-plan и offline-очередью находится в [PLAN.md](../PLAN.md#контракт-start-и-attempts) и [SPEC §11](SPEC.md#11-целевой-контракт-p13-общий-план-и-параллельные-подходы). Исполнитель P13 обновляет этот документ по фактической реализации; наличие нового требования не означает, что оно уже работает.

Интеграция включается отдельно от init:

~~~text
git task hooks install
git task hooks uninstall
~~~

Install привязывает hooks к абсолютному пути запущенного бинарника. Перемещение
бинарника требует uninstall старой интеграции из нового бинарника и нового
install. Путь с пробелами, кириллицей или апострофом экранируется для POSIX shell;
на Windows используются прямые слеши и shell из Git for Windows. Из исходников
следует сначала собрать постоянный бинарник: путь временного `go run` не подходит.
Команда ничего не меняет в глобальных настройках, плане, индексе, ветках и истории.

## Границы автоматической установки

Путь запрашивается у Git через `rev-parse --path-format=absolute --git-path hooks`.
Поддерживается стандартный каталог hooks внутри Git-dir и локальный
core.hooksPath, который также находится внутри этого Git-dir. Относительное
значение разрешается самим Git относительно рабочей копии. Git-dir не
угадывается по имени `.git`. Bare и linked worktree не поддерживаются.

Глобальное/system/command значение core.hooksPath, локальное значение,
указывающее наружу Git-dir, и `/dev/null` дают отказ с инструкцией ручного
подключения. Это консервативная граница: локальная настройка сама по себе не
доказывает, что каталог не используется другими репозиториями. Установка не
переопределяет настройки и не записывает обёртки в общий каталог. Настройки
других репозиториев и глобальная конфигурация не перечисляются.

Все четыре слота сначала проверяются без изменений. Symlink/junction в
компонентах пути, каталог вместо файла, неизвестная обёртка или известный
сторонний менеджер приводят к отказу до установки первого hook.

Поддерживаемая цепочка — свободный слот либо обычный shell-hook с точным
`#!/bin/sh`, без параметров интерпретатора, с LF. Иной интерпретатор, CRLF,
исполняемый двоичный файл или обнаруженные Husky/Lefthook/pre-commit/Overcommit
требуют ручного подключения. Текстовое обнаружение менеджеров консервативно,
не является универсальным распознавателем всех менеджеров. На Unix
неисполняемый файл сохраняется, но его тело не вызывается; на Windows Git
не использует Unix executable bit.

Тело исходного shell-hook исполняется первым в отдельном subshell, внутри
файла с прежним именем. Сохраняются `$0`, `"$@"`, cwd, экспортированное окружение,
stdout/stderr и исходный stdin. `exit`, `exec`, `set -e`, trap и изменения cwd
чужого сценария не отменяют последующий вызов tracking. Затем исполняется
git-task; общий результат равен коду чужого сценария, а при свободном слоте — 0.
Hooks, читающие собственный исходник по `$0`, или исследующие внутренние
переменные shell требуют ручной интеграции: после установки файл содержит
обёртку. Сторонний hook остаётся произвольной программой; его сеть, диалоги,
зависания, сигналы и внешние эффекты не контролируются git-task.

## События и tracking

Сверено 2026-09-30 с [официальными githooks](https://git-scm.com/docs/githooks)
и [core.hooksPath](https://git-scm.com/docs/git-config#Documentation/git-config.txt-corehooksPath).

| Hook | Вход | Действие git-task |
|---|---|---|
| post-commit | Нет аргументов | Сверка фактической локальной истории |
| post-merge | Флаг 0/1 обычного/squash merge | Для 0 — общая сверка через SyncAfterMerge; для 1 — обычная Sync; squash сам не доказывает done |
| post-checkout | Предыдущий OID, новый OID, флаг ветки/файла 1/0 | Проверка входа, включая нулевой предыдущий OID; общая сверка |
| post-rewrite | amend/rebase, возможные будущие дополнительные аргументы; пары old/new OID на stdin | Проверка пар SHA-1/SHA-256 и общая сверка; пары не считаются доказательством интеграции |

Для post-rewrite обёртка сохраняет конечный поток Git во временный файл через
mktemp, передаёт одинаковые байты сначала чужому hook, затем своему и удаляет
файл. Это позволяет сохранить произвольное число строк и будущие extra-info,
не загружая весь поток в память. Scanner собственного обработчика ограничивает
длину отдельной строки; неподдерживаемый ввод предупреждает и не меняет план.
Нужны стандартные sh/mktemp/cat/rm (включены в Git Bash). Ошибка создания файла
оставляет оригинальный поток чужому hook; ошибка чтения/диска диагностируется,
полное восстановление уже прочитанного потока при такой ошибке не обещается.
После принудительного завершения процесса файл может остаться в TMPDIR.

Обработчик `_hook` — внутренний вход, не пользовательская команда управления
задачами. Он не открывает диалог, не использует stdout и возвращает 0 даже при
ошибке аргументов/Git/storage/вывода предупреждения. Сверка ограничена контекстом
15 секунд, использует общую операцию app.sync и ограничения локального
Git-адаптера. Ожидания write.lock нет: занятая блокировка сразу даёт предупреждение.
Чтение stdin относится только к конечному потоку post-rewrite, который Git
передаёт после операции; остальные события получают `/dev/null` в собственном
обработчике. Произвольный прямой вызов `_hook post-rewrite` с бесконечным stdin
не является поддерживаемым способом запуска.

GIT_TASK_OPERATION подавляет собственный hook во время операций start/attach;
GIT_TASK_HOOK подавляет вложенный вызов из собственного обработчика. Чужой hook
при этом исполняется по-прежнему. Статусы и попытки изменяет общая операция сверки:
исполнитель hook не реализует отдельное правило done. Пропущенные события
восстанавливаются обычным sync по правилам [TRACKING.md](TRACKING.md).

В обычном merge Git вызывает post-merge после обновления HEAD, но до удаления
MERGE_HEAD. Это подтверждено порядком `finish` и `remove_merge_branch_state`
в [исходниках Git 2.51.0](https://github.com/git/git/blob/v2.51.0/builtin/merge.c).
Вход `app.SyncAfterMerge` допускает этот оставшийся маркер только при доказанном
завершении: HEAD имеет минимум двух родителей, первый равен ORIG_HEAD,
остальные точно совпадают с MERGE_HEAD, индекс равен дереву HEAD.
Файлы состояния читаются как обычные файлы с полными SHA-1/SHA-256 и LF;
невалидный/отсутствующий ORIG_HEAD или MERGE_HEAD не даёт такого разрешения.
Чтение каждого файла ограничено 4096 × 65 байтами. Другие маркеры незавершённых
операций, index.lock и неразрешённый индекс остаются запретом. Проверка
повторяется перед сохранением, вместе с повторной проверкой доказательства
tracking. Hook не удаляет файлы Git и не считает сам факт события основанием done.
Обычные sync/status/start используют прежнюю строгую проверку MERGE_HEAD.
Если эту переходную фазу нельзя подтвердить, задача сохраняется с предупреждением;
после окончания Git обычный sync сверяет её по фактической истории.

Post-commit не отменяет commit, post-merge не выполняется при конфликте.
После разрешения конфликта tracking вызывается post-commit финального merge
commit. Обёртка сохраняет код чужого post-checkout; checkout/switch могут
нормализовать ненулевой результат в 1 (проверяется сравнением с исходным hook
на том же Git). Переключение к этому моменту уже произошло. Собственный
сбой и недоступный бинарник выводят предупреждение и не добавляют ненулевой код.

## Принадлежность файлов и прерывания

Рядом со слотами находятся `.git-task-<hook>.json` — четыре журнала с
версией, исходными байтами/режимом, путём бинарника и точной ожидаемой обёрткой.
Фактические имена: `.git-task-post-commit.json`, `.git-task-post-merge.json`,
`.git-task-post-checkout.json`, `.git-task-post-rewrite.json`. Они не являются
данными задач и не помещаются в `.git-task`, строгий формат хранения плана
не расширяется. Временно используются `.git-task-hooks.lock` и
`.git-task-pending-*`.

Install/uninstall используют одну межпроцессную блокировку O_EXCL. Каждый
журнал сохраняется и синхронизируется перед заменой hook. Новый hook публикуется
из готового временного файла посредством hard link без перезаписи занятого
слота; для замены существующего hook используется rename после повторной
проверки исходных байтов и режима. Файловая система должна поддерживать эти
операции; недоступная операция даёт ошибку и сохраняет журнал для разбора.
Пути проверяются на symlink, изменения обнаруженного файла не перезаписываются.
Это не общая транзакция четырёх слотов: при отказе возможна диагностируемая
частичная установка. Rename на Windows не обещает гарантии Unix или сохранность
при отключении питания. Неподконтрольный редактор не соблюдает блокировку;
последний промежуток между проверкой и rename не защищён от любой внешней правки.

Повтор install не переписывает неизменённые hooks/журналы. Uninstall сначала
проверяет весь набор: изменённый hook, режим или журнал останавливают операцию
без удаления остальных компонентов. Затем восстанавливает исходный файл и
удаляет только его неизменённый собственный журнал. Если исходного файла не
было, удаляется только неизменённая обёртка. Пользовательские backup и plan.json
не удаляются. Uninstall без интеграции — no-op.

После прерывания не удаляйте журналы или lock по одному возрасту. Сначала
сохраните копии hook, журналов и pending-файлов, убедитесь, что живого процесса
установки нет, и разберите оставшуюся блокировку вручную. Повтор install или
uninstall принимает только точное исходное либо точное установленное состояние
каждого слота. Невалидный журнал/pending-файл требует ручного разбора.
Восстановление не пытается отменить произошедший Git commit/checkout/merge.

## Ручное подключение

Для общего hooksPath или менеджера сначала используйте механизм расширения
самого менеджера. Не изменяйте общий каталог без разрешения его владельца.
Одна лишь установка git-task в PATH не включает tracking.

В обычном shell-hook после выполнения исходной логики сохраните её код и
вызовите (с подходящим абсолютным путём к бинарнику):

~~~sh
git_task_original_status=$?
if [ -z "${GIT_TASK_OPERATION:-}" ] && [ -z "${GIT_TASK_HOOK:-}" ]; then
    GIT_TASK_HOOK=1 '/path/to/git-task' _hook post-commit < /dev/null ||
        printf '%s\n' 'git-task: выполните git task sync.' >&2
fi
exit "$git_task_original_status"
~~~

Для post-merge и post-checkout передайте настоящее имя события и `"$@"`.
Для post-rewrite менеджер должен передать копию исходного stdin обоим
обработчикам, сохранив исходные аргументы и значимый код. Если это невозможно,
оставьте этот hook менеджеру и вызывайте git task sync отдельно. Не считайте
конструкцию с уже прочитанным stdin корректным подключением post-rewrite.

## Подготовленные проверки

Тесты выполняет проверяющий. `cmd/git-task/hooks_test.go:TestRealHooks` строит
реальный CLI и создаёт изолированные репозитории с собственными config,
identity, template, hooks, TMPDIR и бинарниками в путях с пробелами, кириллицей
и апострофами. Никакие пользовательские hooks/config/credentials не используются.

| Критерий P10 | Тест |
|---|---|
| Commit/merge/fast-forward, --again, идемпотентность | TestRealHooks/merge, /fast-forward |
| MERGE_HEAD во время завершённого merge и сохранение строгих guard | TestCheckPostMergeProof, TestSyncAfterMergeUsesCommonTracking |
| Незавершённый merge и изменение Git перед записью | TestRealHooks/unfinished-merge-rejects-hook, TestSyncAfterMergeRechecksGitState |
| Конфликт завершается только после разрешения | TestRealHooks/conflict-resolution |
| Отсутствие диалога, ошибка записи, рекурсия start | TestHookFailureWarnsAndNeverPrompts, TestHookOperationGuardSkipsAllInput, TestRealHooks/tracking-write-lock-warns |
| Чужие argv/$0/stdin и значимый код | TestRealHooks/chain-arguments-stdin-and-exit, /rebase-stream |
| Недоступный бинарник | TestRealHooks/missing-binary-preserves-foreign |
| Повторный install/uninstall, чужие правки | TestInstallNoOpAndRestoreOriginal, TestUninstallPreservesLaterEdits |
| hooksPath, менеджеры, прерывания, symlink/lock | TestLocalAndSharedHooksPath, TestUnsupportedHookPreflight, TestInterruptedInstallCanResumeOrUninstall, TestInstallRejectsLockAndSymlink |
| Работа без hooks и отрицательный squash | TestRealHooks/sync-without-hooks, /squash-does-not-complete |
| Ошибки синтаксиса до Git и точные контракты | TestHooksArgumentsAndHelp, TestEventContracts |

Запустить адресно без кеша, затем общий набор и сборку. Race по hooks/cli и
тестам настоящего CLI уместен, но не доказывает межпроцессные гарантии. Реальные
результаты Windows/Linux/macOS записываются проверяющим; кросс-компиляция не
заменяет выполнение. Если symlink недоступен по правам Windows, соответствующий
пропуск не является подтверждением сценария.
