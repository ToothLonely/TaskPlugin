# P13 — интерфейс и границы реализации

Рабочая ветка: `feat/p13-shared-plan`. Основа требований — текущие документы от 2026-10-04; перенос их незакоммиченных изменений разрешён пользователем в этой сессии.

## Интерфейс

- `git task migrate` явно переводит локальную схему 1 в схему 2. Исходные байты сохраняются отдельно и в backup; незавершённая операция блокирует миграцию.
- `git task team connect --remote <name>` явно включает обмен с существующим настроенным remote. При отсутствии общей ветки публикуется текущий план; существующая общая версия согласуется без перезаписи локальной работы.
- `git task team fetch` получает и применяет общий план без публикации очереди.
- `git task team publish` получает свежую базу и публикует очередь. Максимум три цикла, общий срок 30 секунд. После отказа локальная работа и очередь сохраняются.
- `pause`, `resume`, `complete`, `attach --rebind` принимают `--attempt <точный ID>`. Без селектора допускается один локально связанный незавершённый подход; неоднозначность требует селектор.
- `git task team reconcile` — вход серверного задания: получает общий план и доступные ссылки кода, проверяет доказательства и публикует завершения тем же протоколом. Триггер — изолированный серверный `post-receive`, подготовленный как пример установки; внешняя установка не выполняется.

## Инварианты и точки отказа

В схеме 2 массив attempts хранит все подходы. Их статус определяет агрегированный статус задачи; archived сохраняется явно. ID существующих задач и подходов не меняются. Author неизвестных старых записей отсутствует. Номера представления не служат ключом объединения.

Локальная запись плана и постановка действия в очередь выполняются одной заменой plan.json под существующей блокировкой. Журнал Git-операции включает уже подготовленную очередь, поэтому сбой после создания ветки не требует повторного start. Для автопубликации storage возвращает ID действия из собственного успешно установленного результата Save/Import либо Original/Result текущего journal. App записывает только эти подтверждённые ID в экземпляре текущей команды; CLI создаёт этот экземпляр через ForCommand с общими неизменными Git/storage-зависимостями и отдельными списками ID/уведомлений. Разница общей очереди до/после не определяет авторство: запись другого процесса или другой команды не даёт разрешения на автопубликацию отменённой команды. Без собственного подтверждённого ID проверка публикации не читает storage и не выполняет сеть. No-op и отказ записи ID не возвращают. Если своя мутация сохранена, а затем hook или вывод вернул ошибку, её действие всё равно подлежит публикации; незавершённый journal блокирует её до восстановления. Локальные наблюдения/предупреждения и настройки подключения исключаются из общего снимка.

Сеть выполняется вне storage-lock. После получения и после публикации проверяется исходный локальный снимок. При конфликте сохраняются исходные стороны; успешный push с последующим отказом локальной записи восстанавливается по устойчивому ID действия. Новый commit служебной ветки имеет родителем только полученную служебную версию и содержит только plan.json. Рабочий индекс и checkout кода не участвуют.

Перед replay полученная версия сравнивается с последней подтверждённой общей базой даже при пустой очереди и независимо от local_attempts. Известные задачи/номера, подходы, неизменные данные, история связей, завершения и квитанции не могут исчезать или откатываться обычным fast-forward коммитом метаданных. Такая ручная версия сохраняется отдельно и отклоняется. Новые ID подходов остаются допустимы и могут вернуть done в active. Затем согласование сравнивает базу действия, его результат и полученную версию по полям и ID. Независимые подходы объединяются; устаревшее active не отменяет done. Несовместимые изменения одного поля и коллизии неизменных данных одного ID диагностируются. Полный resolver, ACL и обязательная online-регистрация не реализуются.

Reference-transaction в фазах prepared/aborted только проверяет вход. В committed читает уже записанную remote-tracking ссылку и применяет план под storage-lock, без сети и tracking. Отказ блокировки/согласования не отменяет Git-операцию. Пропущенное событие восстанавливается чтением уже полученной ссылки при следующем status/sync или локальном hook. Вложенные операции транспорта отмечены GIT_TASK_TRANSPORT и пропускают собственный обработчик. Чужой обработчик получает те же stdin/аргументы и сохраняет свой код выхода. Fetch плана не доказывает интеграцию кода.

## Формат схемы 2

Все прежние общие поля Plan сохраняются. Task хранит только `attempts`: незавершённые и завершённые записи. `active_attempt` в JSON отсутствует. В Go ActiveAttempt — временная проекция выбранной записи для существующих операций приложения; при нескольких подходах без выбора она nil и не является отдельным источником состояния.

Attempt сохраняет ID, original_branch, branch, target_branch, base_commit, started_at, rebindings и completion. Добавлены обязательный status (`active`, `paused`, `done`) и необязательный author. Новые start/attach получают author из `git var GIT_AUTHOR_IDENT`; старым записям миграция автора не придумывает. Дата остаётся наблюдением, порядок отображения — started_at с неизвестными датами первыми, затем ID; причинный порядок доставки из дат не выводится. ID новых задач и подходов — случайные 128 бит; отображаемый number независим. При объединении новых задач с одинаковым number переназначается только номер нового пункта, существующие ID сохраняются.

Task.status вычисляется из attempts: без подходов todo, при любом active — active, иначе при любом paused — paused, иначе непустой набор done — done. Archived остаётся явным состоянием задачи, подходы заморожены. Завершение не удаляет запись из массива. Completion.event уникален в согласованной версии плана; независимые коллизии новых событий разрешаются без изменения ID подходов. Это последовательность регистрации, а не точное время завершения. Частичное завершение увеличивает last_event, сохраняя insertion_tail, включая его отсутствие. Курсор вставки меняется при завершении всей задачи; наличие отдельного done-подхода само по себе курсора не требует.

Общий снимок дополнительно содержит `actions: [{id, digest}]` — квитанции уже опубликованных действий. Digest вычисляется по каноническим JSON before/after без зависимости от отступов и порядка ключей. Локальное `team` содержит remote, base, base_commit, pending (`id`, before, after) и local_attempts. Локальные server_events сохраняют пары before/after ещё не обработанного серверного обновления. Эти данные, warnings и observation исключены из общей ветки и JSON export. Очередь и квитанции пока не компактизируются; размер файла растёт с историей действий.

Доступ к подходу без --attempt в подключённом режиме ограничен local_attempts этого clone; совпадение имени чужой ветки само по себе не назначает задачу. Явный --attempt может выбрать известный чужой подход: ACL не реализован. Локальные сведения о Git не переносятся между clone. JSON import принимает схемы 1/2 в пустой план, сохраняет ID и историю, очищает локальные настройки; schema 1 преобразуется в предпросмотре. Миграция собственного plan.json требует отдельного migrate; файл plan.schema-1.json сохраняет точные исходные байты, обычный backup — последнюю валидную версию.

## Серверное включение

Выбран самостоятельный post-receive для обычного Git-сервера с доступом к hooks. Пример [scripts/git-task-post-receive.sample](../scripts/git-task-post-receive.sample) устанавливается администратором; существующий post-receive необходимо сохранить и подключить обработчик к его потоку. Пример не устанавливается автоматически и не обещает интеграции с GitHub/GitLab SaaS. Для другого хостинга нужен отдельный триггер, не входящий в этот артефакт.

Создайте отдельный обычный clone для worker, задайте identity только в его локальном Git config, выполните `git task init --target <branch>` и `git task team connect --remote <name>`. Рабочая target_branch должна соответствовать событию. Серверный процесс получает GIT_TASK_WORKER (путь worker), GIT_TASK_BINARY (абсолютный путь git-task) и GIT_TASK_TARGET (ветка, по умолчанию main). Не используйте рабочий clone разработчика. Пример очищает Git-переменные bare-сервера перед переходом в worker. Сетевые права worker задаёт администратор; код не устанавливает credentials или глобальные настройки.

После обновления target вызывается `team reconcile --before <old> --after <new>`. Событие сначала сохраняется локально, затем worker получает свежий общий план и существующие ссылки подходов/target. Доказательство требует непрерывного before→after, base→tip и tip→after, нового первого родительского коммита работы вне before/base. Пустая ветка, старый достижимый tip, удалённая ветка, squash/cherry-pick и одно только получение метаданных не завершают подход. Ссылки повторно сверяются перед записью. Completion сохраняет target_before; результат ставится в обычную очередь и публикуется тем же ограниченным циклом, что действия разработчика.

Создание/удаление target без обычной пары ненулевых OID пример пропускает; переписанная история диагностируется. Если ветка подхода удалена до обработки или её актуальный tip уже ушёл дальше опубликованного merge, автоматического done нет. История произвольного повторного использования удалённых имён на сервере недоступна: автоматическая сверка опирается на текущие ссылки и достижимость, не обещает доказательства физической непрерывности remote-ref. Требуется сохранение ветки до обработки. Squash остаётся TODO.

При сетевом отказе событие или уже подготовленная очередь сохраняются; повтор — `git task team reconcile` без флагов. Если первая локальная запись не удалась (например, worker занят), post-receive пишет исходные OID и точную команду повторения в stderr; гарантии сохранённой очереди до успешной первой записи нет. Пример выполняется синхронно и может задержать push до общего лимита 30 секунд; успех push кода не отменяется из-за отказа метаданных. Фонового демона, планировщика повторов и автоматического запуска после появления сети нет.

Git-механизмы: [commit-tree](https://git-scm.com/docs/git-commit-tree), [push](https://git-scm.com/docs/git-push), [hooks/reference-transaction и post-receive](https://git-scm.com/docs/githooks). Проверки подготовлены на изолированном bare remote; фактический запуск и приёмку выполняет проверяющий.
