# Локальный релизный кандидат

Кандидат P16 — `0.1.0-rc.1`, не окончательный выпуск. Releases/packages, внешние push,
глобальная установка и настройка системы не выполняются.

Для повторного review после исправления упаковщика используется новый каталог
`.tools/releases/0.1.0-rc.1-r02`. Версия продукта осталась 0.1.0-rc.1;
точный экземпляр отличайте по manifest/SHA256SUMS. Предыдущий каталог сохраняется.

## Сборка

Из корня проекта с Go 1.26.0+; локальный Windows toolchain:

```powershell
New-Item -ItemType Directory -Force .tools/tmp | Out-Null
$env:GOCACHE = "$PWD/.tools/gocache"
$env:GOMODCACHE = "$PWD/.tools/gomodcache"
$env:GOPATH = "$PWD/.tools/gopath"
$env:GOTMPDIR = "$PWD/.tools/tmp"
$env:GOENV = 'off'
$env:GOTOOLCHAIN = 'local'
$env:GOTELEMETRY = 'off'
.tools/go/bin/go.exe run ./scripts/release -version 0.1.0-rc.1 -out .tools/releases/0.1.0-rc.1-r02
```

На Unix аналогичная команда `go run ./scripts/release -version 0.1.0-rc.1
-out .tools/releases/0.1.0-rc.1-r02` с кешами внутри проекта. Скрипт ничего не
устанавливает, не запускает тесты/Git/продукт и не использует сеть.
Нужен **новый** выходной каталог внутри корня; существующий не затирается.
Существующие компоненты пути до root должны быть обычными каталогами:
symlink, Windows junction, неподдерживаемые reparse points и специальные
файлы отклоняются до создания каталога/сборки. Цель junction внутри проекта
тоже не разрешает проход через него. Не меняйте предков назначения во время
упаковки: проверка Lstat не блокирует их конкурентную замену.
После сбоя сохраняется неполный каталог, использовать его нельзя: исправьте
причину и выберите новый `-out`. SHA256SUMS появляется последним, только после
завершения всех сборок. Не меняйте исходники/документы во время упаковки.

Упаковщик расположен в `scripts/release`, отдельно от CLI. Он использует
только стандартную библиотеку и тот же toolchain, которым запущен.
`-trimpath -buildvcs=false -ldflags=-X=main.version=<version>`, CGO_ENABLED=0,
GOARCH=amd64, без загрузки модулей. Бинарник Go не требует установленного Go;
Git остаётся внешней зависимостью. Go LICENSE/PATENTS включены в архив.

| Артефакт | Назначение |
|---|---|
| git-task_0.1.0-rc.1_windows_amd64.zip | Windows/amd64, git-task.exe |
| git-task_0.1.0-rc.1_linux_amd64.tar.gz | Linux/amd64, git-task с mode 0755 |
| git-task_0.1.0-rc.1_darwin_amd64.tar.gz | macOS/amd64, git-task с mode 0755 |
| manifest.json | версия, toolchain, minimum Git, hash входов, hash архива/бинарника |
| SHA256SUMS | SHA-256 трёх архивов и manifest.json |

Архивы содержат бинарник, Markdown-документы и INPUT-SHA256SUMS: упорядоченные
hash исходных .go в cmd/internal/scripts/release, go.mod и документов. SourceSHA256 в manifest —
hash этого списка; тестовые исходники учитываются, но не исполняются и в архив
не входят. Локальные AGENTS.md, SKILLS.md и PLAN.md не участвуют в упаковке
и hash входов; наличие этих файлов у разработчика не требуется для сборки
из обычного клона. LICENSE-STATUS.md удалён по запросу владельца.
Исторический кандидат R02 не переупаковывается автоматически.
Scripts/CI исходники остаются в репозитории.
GO-LICENSE/GO-PATENTS отдельно фиксируют условия toolchain.
Для точно такого кандидата сверяйте manifest и SHA256SUMS, а не только версию.
После изменений кандидата его надо собрать заново в новый каталог.
Побайтовая воспроизводимость между разными toolchain/средами не обещается.
Checksum проверяет целостность, но не заменяет подпись или доверенный канал.

## Передача проверяющему P16

Тесты исполнителем не запускаются. Проверяющему необходимы:

- `go vet ./...`, `go build ./...`;
- `go test -count=1 -timeout=90s -run '^(TestArchiveContentsAndModes|TestReleaseRejectsInvalidRequest|TestReleaseEnvironment|TestReleaseOutputDirectory|TestReleaseOutputPathCase|TestReleaseOutputJunctionRejected)$' ./scripts/release`;
- Windows-регрессия TestReleaseOutputPathCase меняет регистр диска,
  каталогов и обоих сразу. Каждая проверка запускается в отдельном процессе
  с тайм-аутом 5 секунд; зависший дочерний процесс завершается;
- TestReleaseOutputDirectory проверяет относительный/абсолютный путь,
  отмену, отказ на root/соседний каталог/выход за границы и symlink.
  Недоступные symlink явно отмечаются SKIP, а не PASS;
- Windows-регрессия TestReleaseOutputJunctionRejected создаёт junction
  без привилегии symlink с целью внутри и вне переданного тестового root.
  Обе цели остаются в одном t.TempDir; проверяются отказ для самой ссылки,
  прямого и вложенного назначения, отказ run до записи и сохранность
  содержимого цели. Ошибка создания junction — FAIL, а не скрытый SKIP;
- повторить диагностическую сборку упаковщика с абсолютным Windows -out
  в другом регистре внутри workspace и новым каталогом; проверить отказ
  перезаписи существующего -out. Проверить новые SHA256SUMS/manifest,
  INPUT-SHA256SUMS и совпадение hash продуктовых бинарников с прошлым кандидатом.
  Для R02 дополнительно проверить, что junction-предок отклоняется до записи
  и не изменяет целевой каталог; достаточно изолированного root и соседней
  цели внутри workspace, выход за workspace для воспроизведения не нужен.

Уже успешные Git-сценарии BinaryCommands/RealHooks и три app-сценария,
проверка установки/обновления/uninstall и локальный/командный цикл записаны
проверяющим в PLAN.md. При неизменных продуктовых исходниках и binary_sha256
для исправления путей упаковщика повторно их автоматически не назначать.

Перед установкой hooks задайте в тестовом окружении собственные identity,
config/template и очистите GIT_* указатели чужих репозиториев; не меняйте
пользовательские Git-настройки. Снимите plan/очередь, чужие hooks, индекс,
код и refs до установки/обновления/удаления и сравните после.
Offline-доставку выполняйте publish с прежними action/attempt ID.
Ручные сценарии README — часть приёмки, их не заменяет тест упаковщика.
Недоступные Linux/macOS и оставшаяся матрица относятся к P17;
кросс-сборка не является положительным результатом этих проверок.
Security выполняет проверяющий через настроенный маршрут CHECKS.md;
полный набор проекта — только P18. Финальный сквозной отчёт — P17.
