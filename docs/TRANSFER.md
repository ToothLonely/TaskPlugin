# Импорт и экспорт локального плана

Контракт — [SPEC §8](SPEC.md#8-импорт-и-экспорт). Обменные форматы разбираются
в `internal/transfer`, приложение координирует хранение в `internal/app`,
а аргументы, предпросмотр и подтверждение находятся в `internal/cli`.

~~~text
git task init
git task import checklist.md
git task import checklist.md --yes
git task export
git task export --format json --output snapshot.json
git task import snapshot.json --format json --yes
~~~

Импорт принимает только пустой инициализированный план. Задачи в архиве также
делают план непустым. Предпросмотр в stderr показывает формат, полный порядок,
количество, ID, номера, состояния, путь назначения и `target_branch`.
Без `--yes` нужен терминал: `да`, `yes` или `y` подтверждают импорт;
пустой ответ и любой другой ответ отменяют его. Отказ, EOF и прерывание дают
код 130 без записи. `--yes` пропускает диалог после тех же проверок.

Весь исходник читается и проверяется до предпросмотра. Применяется именно
подготовленный снимок исходника; последующие правки исходного файла автоматически
не подхватываются. Пока пользователь отвечает, блокировка не удерживается.
Перед записью приложение сравнивает точные байты плана, проверяет отсутствие
незавершённой операции и пустоту назначения. Общая запись хранения ещё раз
проверяет исходник под межпроцессной блокировкой, валидирует полный результат,
сохраняет backup и заменяет plan.json. Отмена и неверный ввод не создают backup.
Прерванная запись оставляет диагностируемый pending-файл, а не часть задач.
Границы защиты от внешнего редактора остаются описанными в [STORAGE.md](STORAGE.md).

## Markdown

Ввод — UTF-8 с необязательным начальным BOM и LF/CRLF. Допустимы только
плоские строки без отступа:

~~~text
# Личный план
- [ ] Добавить профиль 🙂
- [x] Подготовить проект
- [X] Готовый пункт без известной даты
~~~

Пробельные строки и ATX-заголовки с 1–6 символами `#` игнорируются.
После `]` нужен один пробел-разделитель; остаток строки сохраняется буквально,
включая дополнительные пробелы. Заголовки задач могут совпадать: ID и номера
будут разными. Вложенность, продолжения, прочий текст, блоки кода, другие маркеры,
пустые названия и отсутствие пунктов отклоняются с номером строки, когда он есть.

Все задачи сначала создаются как todo в порядке входа. Затем отмеченные пункты
завершаются в том же порядке: одна запись `attempts` с `source: imported`,
без дат, ветки и SHA. ID подхода имеет вид `imported-task-NNN`. Todo не получает
`attempts`. Последний отмеченный пункт становится опорой следующих добавлений;
без отмеченных пунктов опора — последний импортированный todo.

Экспорт — все задачи в полном порядке: `[x]` только для текущего done,
`[ ]` для todo, active, paused и archived. Потери ID, описаний, связей, истории
и различий остальных состояний объясняются в stderr. Название с переводом строки
отклоняется с предложением JSON. Markdown служит представлением для чтения:
исходник не перезаписывается и не синхронизируется с plan.json.

## Полный JSON

Формат совпадает с канонической схемой 1 из [MODEL.md](MODEL.md): настройки,
ID и номера, порядок, ревизии, состояния, `active_attempt`, завершённые `attempts`,
события и хвост вставок сохраняются. Используется строгий декодер модели;
неизвестная версия, поля, дубли ключей/ID/номеров, null и нарушенные ссылки или
доменные инварианты отклоняются без исправления данных. Никакой второй схемы нет.

Импорт принимает `target_branch` снимка даже при её отсутствии в локальном Git.
Ветки, refs и hooks не создаются. Сохранённая история остаётся историей;
наблюдения требуют локальной перепроверки будущим sync. Это обмен снимками,
а не транспорт или согласование разных clone из отложенного P13.

Для пустого назначения `Store.Import` сохраняет исходную revision, включая 0,
через тот же протокол записи. Обычный `Store.Save` по-прежнему требует увеличения
revision при изменении. Такое исключение нужно для точного переноса снимка;
оно проверяет пустоту под блокировкой и не разрешает сброс существующих задач.

## Файл экспорта

Без `--output` данные идут в stdout; JSON не содержит диагностических строк.
Export не выполняет sync и не меняет план. Невалидное хранилище, lock, pending
и незавершённая операция блокируют экспорт до восстановления.

Существующий output, включая ссылку, каталог или исходник импорта,
не перезаписывается. Запрещено создание файлов внутри `.git-task` и каталогов
Git. Родитель разрешается через файловую систему; проверка идентичности
каталогов учитывает ссылки и нечувствительность к регистру.
Сначала полностью записывается и синхронизируется временный файл рядом с output,
затем `os.Link` публикует готовый снимок без замены существующего пути.
Временный файл удаляется; ошибки записи, публикации и очистки возвращаются.
Родительский каталог должен существовать, файловая система должна поддерживать
hard links. Защита от любого конкурентного переименования родительских каталогов
внешним процессом и отключения питания не обещается.
