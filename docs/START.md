# Запуск и привязка

Выбор разрешается в постоянный ID под общей
блокировкой хранилища. Проверки запроса и подготовка результата предшествуют
мутациям Git; фактическое состояние проверяется также после них.
Исходный план и полный подготовленный результат записываются в локальный журнал
до создания ветки. История attempts меняется только доменной операцией завершения.

Границы отказа: до журнала; после журнала; после создания ref; после checkout;
после замены plan.json; при закрытии журнала. На последних четырёх границах нельзя
повторять создание или удалять ветку для отката. Незавершённый журнал блокирует
мутации, чтение плана остаётся доступно с предупреждением.

Ветка создаётся условным update-ref (ожидается отсутствие ref), с ID операции
в reflog, затем переключается checkout --no-overwrite-ignore. Собственные будущие
hooks получают GIT_TASK_OPERATION; чужие hooks продолжают работать. Владение
проверяется по reflog, ref и HEAD, а не по одному совпавшему имени. Изменившиеся
основание, ref, HEAD, журнал или план требуют явного восстановления. Журнал
содержит исходные байты и подготовленный результат, поэтому восстановление после
записи плана закрывает только журнал, сохраняя revision и backup.

Attach не переключает ветки; журнал и та же блокировка защищают запись привязки.
Rebind сохраняет ID подхода. Пользовательский doctor относится к P14; P06
предоставляет операцию восстановления для его будущего вызова и тестов.

## Команды

~~~text
git task start feature-profile
git task start feature-api --id task-003
git task start profile-v2 --title "Добавить профиль" --again
git task start experiment --new "Проверить гипотезу" --from refs/tags/v1
git task attach existing-branch --id task-004
git task attach replacement-branch --id task-004 --rebind
~~~

Флаги разрешены до и после имени ветки. Отсутствующее имя, лишние аргументы,
повтор флага и конфликт селекторов отклоняются до открытия репозитория.
`--id` не принимает number/номер строки вместо ID; `--title` сохраняет регистр
и пробелы и ищет по всем статусам. Неоднозначность требует `--id`.
`--select` зарезервирован для P07 и сейчас явно отказывает без открытия плана.

Основание по умолчанию — локальная target_branch, даже из другой ветки.
Start из detached HEAD отказывает до создания журнала и ветки: сначала нужно
явно выбрать ветку. Attach не переключает HEAD и допускает detached состояние.
`--from` принимает буквальную локальную ветку, тег, полный ref
или однозначный шестнадцатеричный ID объекта, разрешаемый в commit. Несколько
совпадений, rev-выражения и отсутствующая target_branch запрещены.

Start требует чистого индекса и дерева, включая неигнорируемые untracked-файлы.
Attach/rebind допускают dirty tree. Обе операции отказывают при незавершённых
merge/cherry-pick/revert/rebase/bisect/sequencer, чужом index.lock и при
неразрешённых записях индекса (в том числе после `git merge --quit`).
Ни одна операция не выполняет сеть, stash/reset, force checkout или удаление
ветки. Защита игнорируемых файлов обеспечивается `--no-overwrite-ignore`.

## Журнал и восстановление

`operation.json` версии 1 содержит исходные байты plan.json (`original`),
полный подготовленный результат (`result`), намерение (`intent`) и SHA-256
канонического JSON с пустым значением digest. Байты двух планов представлены
base64, чтобы сохранить даже исходное форматирование. Намерение содержит ID
операции, постоянный ID задачи, тип start/attach/rebind, branch, исходные HEAD/ref
и commit, основание и снимок target_branch. В планах сохранены ревизии, исходный
статус, история и ID подхода. Для start/attach ID новой попытки равен ID операции;
rebind использует новый ID операции, сохраняя ID подхода.

SHA-256 выявляет повреждение, но не является подписью от намеренной подделки.
В ходе операции дополнительно сравниваются точные байты самого журнала.
Запись журнала использует синхронизированный временный файл и hard link с
отказом на занятый путь. Это тот же набор файловых ограничений, что у init.

| Наблюдение | Результат RecoverStart |
|---|---|
| Исходный план, ветка отсутствует, прежний HEAD | Закрыть намерение без Git-операции и записи плана |
| Исходный план, ветка и HEAD соответствуют журналу, reflog подтверждает создание | Сохранить подготовленный результат и закрыть журнал |
| План побайтово равен результату, Git-эффект подтверждён | Только закрыть журнал, сохранить revision/backup |
| Ветка создана, но HEAD ещё прежний | Отказ; пользователь явно завершает переключение перед повторной проверкой |
| Изменён план, журнал, основание или ветка; владение не подтверждено | Отказ с сохранением всех данных |

Для attach/rebind проверяется существующая ветка и её исходный commit; checkout
и доказательство создания не требуются. Повтор успешного rebind — no-op.

Обычные мутации при наличии журнала отказывают. Status читает план с
предупреждением; оставшаяся после смерти процесса write.lock отдельно блокирует
чтение по контракту хранения. Возраст блокировки не разрешает снять её.
Тест аварии ждёт завершения известного дочернего процесса перед имитацией
отдельно разрешённого unlock; RecoverStart никогда не снимает блокировку сам.

Если сторонний post-checkout вернул ошибку после подтверждённого переключения,
связь сохраняется, CLI возвращает ненулевой код и сообщает, что задача уже
запущена. Нельзя повторять создание ветки, предполагая отсутствие эффекта.

Не гарантируется защита от любого внешнего Git-процесса/редактора, изменившего
состояние между последней проверкой и действием. Параллельные операции CLI
сериализованы общей write.lock; обнаруженное расхождение не затирается.
Удалённый/изменённый reflog даёт отказ восстановления, а не догадку о владении.
Наблюдения дальнейшего tracking и вывод doctor остаются P09/P14.

Успешный start сохраняет context вызывающей стороны на всём пути, без скрытого
короткого таймаута сохранения. После ошибки создания ref отдельная проверка
фактического состояния ограничена 30 секундами и допускает завершение диагностики
после отмены исходного context; её неудача оставляет журнал для разбора.
