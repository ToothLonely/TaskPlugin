# Локальная сверка P09

> Уточнение 2026-10-04: ниже описана принятая реализация P01–P12 со схемой 1. Целевой контракт P13 с несколькими attempts, author, общей веткой git-task-plan и offline-очередью находится в [PLAN.md](../PLAN.md#контракт-start-и-attempts) и [SPEC §11](SPEC.md#11-целевой-контракт-p13-общий-план-и-параллельные-подходы). Исполнитель P13 обновляет этот документ по фактической реализации; наличие нового требования не означает, что оно уже работает.

Общая операция app.Sync обслуживает sync, status и hooks. Tracking читает
Git через адаптер и возвращает наблюдение, предупреждения либо доказательство;
только app применяет доменные переходы и сохраняет весь результат одной записью.
Active и paused сверяются в порядке плана; archived не участвует.

## Доказательства

Каждый подход имеет собственную baseline: исходный tip, текущую цель и отпечаток
целевого reflog. Start дополнительно имеет уникальную запись создания ветки
`git-task start <attempt-id>`. Attach/rebind запоминают отпечаток существующего
reflog. Отпечатки — SHA-256 префикса локального журнала, не секреты и не подписи.
Отсутствующий журнал, потеря префикса или разрыв цепочки означают неопределённость;
совпадение имени/SHA не восстанавливает принадлежность пересозданной ветки.

При sync фиксируется собственный немержевый commit, достижимый из текущего tip,
но отсутствующий одновременно в текущей цели и исходном основании. Пустая ветка,
fast-forward из main и merge-обёртка над main без собственных commit не подходят.
Это свидетельство интеграции истории, без оценки содержания/качества кода.

Наблюдение работы и её target_commit образуют неделимое доказательство. Если
собственная работа уже вошла в цель, но актуальный tip ещё вне неё (например,
после обратного merge main в work), промежуточный sync/status без новой собственной
работы сохраняет весь прежний снимок и его reflog-префиксы. Нельзя передвинуть
target_commit на историю, содержащую сохранённый work_commit. Непрерывность и
актуальные refs всё равно проверяются; новое собственное наблюдение вне цели
или переписывание истории создаёт новую baseline по обычным правилам.

Автоматическое done требует сохранённого наблюдения работы вне цели, актуального
tip, непрерывных журналов ветки/цели и достижимости всего актуального tip из цели.
Проверяются все изменения refs после наблюдения, а не только последний SHA.
Reset/rebase/amend сбрасывают доверие к старой работе. Новое наблюдение вне цели
может начать свежую цепочку; уже интегрированная переписанная работа требует
ручного complete. Удаление/пересоздание требует явного rebind.

Для rebind на то же имя app проверяет непрерывность ветки по тому же правилу
префикса/цепочки reflog, что и sync, включая совпадение последнего SHA с ref.
Подтверждённая связь, в том числе продвинувшаяся без удаления, остаётся no-op.
Потерянный префикс, разрыв либо отсутствующий журнал допускают явное обновление
связи: история получает запись from=to, ID подхода и исходная ветка сохраняются,
base_commit и observation заменяются свежей baseline без work_commit. Старые
завершённые attempts не меняются. Даже совпадающий SHA не переносит старую работу;
при недоступном reflog новое завершение по-прежнему не считается доказанным.

По первой родительской цепочке цели от сохранённого target_commit определяется
первое включение актуального tip. Merge-доказательство имеет несколько родителей,
tip входит через не первого родителя и отсутствует в первом. При fast-forward
первый включающий commit — сам tip. Commit, актуальный tip в WorkCommit и merge_kind сохраняются
в completion; observed_at — время обнаружения, completed_at не выдумывается.

Пропущенный post-merge восстанавливается из сохранённой работы и текущего графа.
Если пропущены все наблюдения работы, одной ancestry недостаточно: выводится
`unobserved_work`, подход остаётся active/paused. Reflog не используется для
угадывания порядка человеческой работы по секундным часам или текстам commit.
Squash/cherry-pick/совпадение tree не дают автоматического завершения.

## Отказы и границы

Незавершённая Git-операция блокирует финализацию, dirty tree и detached HEAD
допускаются. Отдельный вход post-merge допускает ещё не удалённый MERGE_HEAD
только после проверки завершённого merge по HEAD, его родителям, ORIG_HEAD
и индексу; правила и повторная проверка описаны в [HOOKS.md](HOOKS.md).
Обычные sync/status остаются строгими, остальные маркеры операций не игнорируются.
Нет цели/ветки/объекта — диагностика без done. Иные ошибки Git и
отмена возвращаются как error, отрицательная ancestry распознаётся только по 1.
Перед сохранением повторно проверяются tip, цель и журналы; обнаруженная внешняя
правка отменяет запись. Git не соблюдает lock плана: не обещается транзакция
между Git и JSON или обнаружение любой подмены после последней проверки.

Reflog и обход цели ограничены бюджетом 4096 записей/commit и 4 MiB журнала.
Превышение бюджета, expire/gc журналов, недостаточные объекты и потеря baseline
дают неопределённость. Локальные журналы не являются защитой от намеренной
подделки. JSON-импорт сохраняет наблюдения, но сверка проверяет их против местного
Git; чужие отпечатки не дают доверия автоматически. Схема 1 ещё не выпускалась;
необязательное поле observation добавлено с явной валидацией.

No-op не записывает время опроса, plan.json, revision или backup. Несколько
завершений регистрируются в порядке плана одной проверяемой заменой JSON.
Сбой до замены оставляет прежнее согласованное состояние и pending-кандидат;
сбой после замены сообщает уже сохранённый результат, повтор не дублирует ID.
Status при operation.json показывает сохранённый план без сверки. После done
потеря достижимости completion даёт предупреждение без отмены истории.

Контракты Git: [merge-base](https://git-scm.com/docs/git-merge-base),
[rev-list](https://git-scm.com/docs/git-rev-list),
[reflog](https://git-scm.com/docs/git-reflog).
