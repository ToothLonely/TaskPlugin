# Git Task — спецификация первой версии

Нормативная основа — [PLAN.md](../PLAN.md), включая последние решения пользователя. Этот документ задаёт поведение продукта; состояние разработки хранится только в PLAN.md. Обоснования и допущения: [DECISIONS.md](DECISIONS.md). Проверяемые сценарии: [ACCEPTANCE.md](ACCEPTANCE.md).

## 1. Назначение и границы

`git-task` — Go CLI, вызываемый как `git task`, для личного и подключаемого общего плана, связанного с Git-ветками. Действует принятая в P13 схема 2 из §11–12 и [P13-IMPLEMENTATION.md](P13-IMPLEMENTATION.md). Разделы 2–10 сохраняют базовый контракт P01–P12; прежние правила схемы 1 об active_attempt, единственном подходе и attempts только после done заменены §11–12. «В работе» означает наличие незавершённых подходов, а не обязательно текущий checkout. Завершение подхода означает доказанную интеграцию его работы в целевую ветку или явное ручное/импортированное завершение; задача done только при непустом наборе всех известных done. Это не оценка качества, тестов или публикации кода.

Один план находится в `.git-task/plan.json` в корне рабочей копии; переключение обычных веток использует тот же файл. Несколько задач и несколько подходов одной задачи могут быть в работе. Связанный подход имеет одну ветку; одна локальная ветка не обслуживает две локальные незавершённые связи, включая paused. Чужая общая запись не назначается локальной ветке автоматически.

Локальный режим, status/sync и hooks не требуют сети и не выполняют fetch/push/lazy fetch. Командный режим явно подключает отдельную git-task-plan того же remote и сетевую публикацию пользовательских мутаций с offline-очередью. CLI подключения и селектор --attempt определены в §12. Обязательного сервера/daemon для личного режима нет. Squash отложен; import/export поддерживает схему 2 и исключает локальные настройки, наблюдения и очередь.

Целевые ОС — Windows, Linux, macOS. Версии Go/Git и архитектуры фиксируются на P02/P15 по используемым возможностям; поддержка подтверждается исполнением матрицы. По прямому решению пользователя 2026-10-05 P17 принят по доступным Windows/amd64 проверкам; native Linux/macOS и Windows symlink без SKIP отложены в TODO-04 PLAN.md и не блокируют P18. Этот документ не объявляет отложенные платформы/случаи проверенными; полный финальный Windows-набор P18 остаётся обязательным.

Минимальная поддерживаемая конфигурация: обычный репозиторий с единственным рабочим деревом и полной локальной историей. В первой версии linked worktree, а также основной репозиторий с зарегистрированными дополнительными worktree, bare, shallow и partial clone диагностируются как неподдерживаемые для операций плана. `doctor` доступен для объяснения ограничения без мутаций. Это допущение P01, см. D04; работа с несколькими деревьями не должна создавать несколько конкурирующих планов.

## 2. Общий интерфейс

Справка, собственные сообщения и диалоги — на русском; команды, флаги, JSON-ключи и значения состояний — на английском. Названия/описания — Unicode. Сообщения самого Git могут иметь язык установленного Git; программа не разбирает их как машинный протокол.

Команды не подразумевают пользовательский ввод, кроме `--select`, подтверждения import/complete/repair и явного запуска редактора. В неинтерактивной среде команды, которым нужно подтверждение, требуют `--yes`; `--select` всегда требует терминал. Обычный start работает без терминала. `--yes` не отменяет валидацию и не означает force.

Флаги разрешены до и после позиционных аргументов; `--` завершает разбор флагов. Неизвестный флаг, лишний аргумент, пропущенное значение, повтор одиночного флага или конфликт опций — ошибка до диалога, sync и записи. `--help`/`help [command]`, `--version`/`version` работают без репозитория; отсутствие команды показывает справку с кодом 0.

Коды выхода: 0 — успех, включая no-op и диагностические предупреждения о неопределённости; 2 — неверный синтаксис; 1 — отказ по состоянию, ошибка Git/хранения, неподдерживаемая среда или найденная doctor проблема; 130 — отмена пользователем, включая EOF при ожидаемом ответе. Ошибка после внешнего эффекта явно сообщает, что уже произошло, и указывает `doctor`; ненулевой код не обещает откат Git.

stdout содержит результат, stderr — ошибки, предупреждения и prompts. `status --json` выводит ровно один JSON-объект без ANSI/сообщений Git. При ошибке, исключающей достоверный снимок, stdout пуст и код ненулевой. Частичный достоверный снимок с неопределёнными связями допустим с предупреждениями и кодом 0.

## 3. Реестр команд

Ниже `id` всегда означает точное JSON-поле `id`; `number` и позиция не являются алиасами. Заголовки в кавычках — один аргумент оболочки. Квадратные скобки в синтаксисе обозначают необязательную часть.

| Синтаксис после `git task` | Результат и основные ограничения |
|---|---|
| `help [command]`, `version` | Справка и версия; до реализации команды help не выдаёт её за работающую |
| `init [--target <branch>]` | Создаёт пустой план и локальное исключение; default target — `main`, без угадывания по HEAD/remote |
| `add <title> [--description <text>] [--after <id> / --before <id> / --end]` | Новый todo с новым ID/номером; по умолчанию вставка по разделу 6 |
| `start <branch> [--id <id> / --title <title> / --new <title> / --select] [--from <ref>] [--again]` | Создаёт и переключает ветку, начинает подход; раздел 4 |
| `attach <branch> --id <id> [--rebind]` | Связывает существующую локальную ветку, не переключает её; раздел 5 |
| `edit --id <id> [--title <title>] [--description <text>]` | Меняет только указанные поля; без этих флагов открывает редактируемый документ title/description в редакторе |
| `move --id <id> (--after <id> / --before <id> / --end)` | Переносит один пункт; ровно один способ позиционирования |
| `pause --id <id>` | active → paused, сохраняет подход, без checkout |
| `resume --id <id>` | paused → active после успешного переключения на связанную ветку |
| `complete --id <id> [--commit <oid>] [--yes]` | Явное ручное завершение; раздел 5; не выполняет merge |
| `archive --id <id>` | Убирает задачу из рабочего списка, сохраняет данные, не удаляет код/ветку |
| `status [--json]` | Локальная сверка и экран возвращения; раздел 9 |
| `show --id <id>` | Чтение одной задачи, включая archived, без скрытого sync |
| `sync` | Сверка всех текущих подходов с локальным Git, без сети и диалога |
| `import <path> [--format markdown / --format json] [--yes]` | Полный предпросмотр и импорт в пустой инициализированный план; default markdown |
| `export [--format markdown / --format json] [--output <path>]` | Снимок без sync; default markdown в stdout; существующий output не перезаписывает |
| `hooks install`, `hooks uninstall` | Явная установка/удаление локальной интеграции; init не устанавливает hooks |
| `doctor [--repair <action>] [--yes]` | Диагностика; действия `recover-start`, `restore-backup`, `unlock` только явно, раздел 10 |

`--after`, `--before`, `--end` взаимоисключающие; ссылка на отсутствующий ID или на себя в move — ошибка без изменений. Допускаются опоры archived: они остаются в полном порядке. Пустой/пробельный title запрещён. Непустой title сохраняется буквально, включая крайние пробелы; description может быть пустым. Нет неявной Unicode-нормализации. ID и number не меняются при edit/move.

Не вводятся `reopen`, `--task`, `start -b` и генерация имени ветки. `sync --remote`, поиск в меню, автодополнение, подзадачи, несколько веток на подход, командная работа и интеграции с редакторами относятся к расширениям P18. Отдельная команда `note` не включается: краткий контекст можно хранить в description. Базовое открытие редактора командой edit входит в первую версию.

## 4. Запуск задачи

### 4.1. Выбор

1. Сначала полностью проверить синтаксис. Во всех режимах требуется ровно одно непустое имя branch. Отсутствие имени, лишние позиционные аргументы и `-b` отклоняются до меню и любых мутаций, включая журнал.
2. Без селектора выбирается первый todo по текущему массиву порядка, с пропуском done/active/paused/archived. Нет todo — «Нет не начатых задач», без меню/новой задачи/ветки.
3. `--id` ищет точную строку id по всем задачам. Для `id="task-003", number="T-003"` значения `3` и `T-003` не подходят, если нет отдельной задачи с буквально таким id.
4. `--title` ищет точное полное значение по всем задачам до проверки статуса. Регистр, пробелы и Unicode значимы. Пустое/пробельное значение запрещено. Нет совпадений — «Пункт с таким title не найден». Несколько совпадений — ошибка со списком id и предложением `--id`, даже если один пункт todo, а другой archived. Создание вместо поиска запрещено.
5. `--id`, `--title`, `--new`, `--select` взаимоисключающие, повтор одного селектора тоже ошибка. Выбранный пункт нельзя молча заменить другим. После разрешения title операция использует постоянный ID и проверяет версию выбранного пункта перед мутацией.
6. Обычный явный выбор todo допустим. Для done требуется `--again` с подсказкой того же селектора; для paused — resume; для active — ошибка второй попытки; для archived — ошибка. Автоматический запуск их пропускает.
7. `--again` допустим только для done с ровно одним явным `--id` или `--title`. Нет селектора, другие состояния, `--new` и `--select` — ошибка. Это само по себе подтверждение нового подхода, дополнительного вопроса нет. Остальные проверки не обходятся.
8. `--new` создаёт задачу по правилам add, но сохраняет её только вместе с успешным стартом. Ошибка до создания ветки не оставляет новый todo. `--select` показывает todo в порядке плана, недоступные состояния с объяснением, действие создания и отмену. Номер меню — только временный выбор строки, не ID.

Меню показывает основание и branch; неверный номер повторяет запрос, не выбирая соседний пункт. Окончательный выбор строки либо ввод title новой задачи запускает общую операцию start. EOF/отмена до выбора не создают журнал/ветку/задачу. Блокировка не удерживается во время диалога; после него конфликт версии требует повторного выбора, а не автоматического перенаправления.

### 4.2. Ветка и транзакция

Основание по умолчанию — текущий локальный `refs/heads/<target_branch>`, независимо от HEAD. `--from` принимает существующую локальную ветку, полный ref, тег или однозначный commit ID, разрешаемый в commit без сети; неоднозначное имя и отсутствующий объект — ошибка. Произвольные rev-выражения не поддерживаются в первой версии. Основание сохраняется как commit ID. Цель завершения остаётся target_branch.

Имя новой ветки — короткое локальное имя, валидное по Git, без начального `-`, полного префикса `refs/` и специальных сокращений вроде `@{-1}`. Используются отдельные аргументы, валидированные полные refs и допустимые конкретной командой разделители. Занятое имя — ошибка; нет суффиксов, переиспользования и force. Основание, свободность имени, версия задачи, уникальность связи и отсутствие tracked `.git-task/` в целевом дереве проверяются перед изменениями. Гонка создания имени — отказ, а не присвоение появившейся чужой ветки.

Start/resume требуют чистых индекса и рабочего дерева: staged, unstaged и неигнорируемые untracked файлы блокируют переключение. Игнорируемые файлы не удаляются и не перезаписываются; при конфликте с целевым деревом операция отказывает. Нет скрытых stash/reset/force-switch. Это консервативное правило продукта, не утверждение, что любой Git checkout запрещён при dirty tree.

Перед внешним эффектом сохраняется намерение с ID операции/подхода, выбранным ID и версией задачи, исходным статусом/историей, HEAD, основанием и branch. После фактического создания и переключения выполняется одно обновление: новый active_attempt, статус active, прежние attempts без изменений. Для done нет промежуточного todo. Init/add/edit и другие чистые изменения плана не создают ветки.

Сохранение plan.json и закрытие журнала — разные шаги. До замены plan.json журнал должен содержать проверяемое описание подготовленного результата именно этой операции: ожидаемую ревизию и полное содержимое результата либо его контрольный отпечаток, связанные с ID операции, задачи и подхода. Исходный снимок тоже сохраняет ревизию и содержимое/отпечаток всего плана. Это позволяет отличить исходное состояние, уже сохранённый собственный результат и постороннее изменение, даже если процесс не успел отметить в журнале успешную запись. Совпадения только статуса, имени ветки или ID подхода недостаточно. Формат доказательства определяет P05/P06; полагаться на атомарность двух файлов нельзя. Для resume действует тот же протокол: меняется paused → active, ID подхода и attempts сохраняются.

Если Git вернул ошибку, сначала проверить фактические ref/HEAD: post-checkout мог завершиться ошибкой уже после переключения. Нельзя слепо повторять создание или удалять ветку для «отката». Если требуемое состояние достигнуто и владение операцией подтверждено журналом, сохранить связь, сообщить о совершённом запуске и ошибке hook (код 1). При сомнениях сохранить журнал и исходные метаданные, отправить к doctor. Незавершённый журнал блокирует новые мутации плана до явного восстановления; чтение доступно с предупреждением. Собственные hooks в ходе операции не входят рекурсивно в storage.

Ошибка/отмена до создания ветки оставляет исходные задачу и attempts; журнал без эффекта безопасно закрывается. Прерывание после создания может оставить ветку и журнал при прежнем статусе. Повтор успешной команды не начинает новый подход: пункт уже active. Смена ref основания или обнаруженная внешняя правка во время операции требует сверки/восстановления, а не записи поверх изменившегося плана.

Прерывание после сохранения подготовленного результата, но до закрытия журнала, оставляет уже правильный план и незавершённое обслуживание операции. При подтверждении этого случая recover-start закрывает только журнал: не повторяет Git, не сохраняет план заново, не создаёт задачу/подход и не меняет attempts, ревизию или backup. Наличие журнала само по себе не доказывает, что запись плана ещё предстоит. Точные ветви восстановления — в §10.

### 4.3. Примеры

| Исходный порядок | Ввод | Результат |
|---|---|---|
| T-001 done, T-002 active, T-003 todo | `git task start feature-profile` | T-003 active; feature-profile от target_branch |
| T-001 done, T-002 todo, T-003 todo | `git task start feature --id task-003` | T-003 active |
| Результат предыдущей строки, HEAD=feature | `git task start feature-2` | T-002 active; feature-2 также от target_branch |
| T-003 done | `git task start profile-v2 --title "Добавить профиль"` | Ошибка с подсказкой добавить --again; всё сохранено |
| T-003 done, title уникален | `git task start profile-v2 --title "Добавить профиль" --again` | Новый active_attempt, done → active, история сохранена |

## 5. Состояния и подходы

| Состояние | Текущий подход | История и разрешённые действия |
|---|---|---|
| todo | Нет | До первого done нет attempts; start/attach, complete, archive |
| active | Ровно один active_attempt | pause, complete, автоматическое завершение, rebind, archive |
| paused | Тот же active_attempt | resume, complete, rebind, archive; tracking может доказать done и во время паузы |
| done | Нет | Непустой attempts; start с явным селектором и --again, archive |
| archived | Сохранённый незавершённый active_attempt возможен, но заморожен | История сохраняется; edit/move/show разрешены, tracking и запуск отключены |

Archive сохраняет незавершённый подход в active_attempt без фиктивного завершения; статус archived делает его историческим снимком, а не живой связью. Ветка освобождается для явного attach другой todo-задачи, код не меняется. Команды unarchive нет в первой версии. Это выбранная минимальная семантика D05, которую должна проверить модель P03.

Повтор pause для paused, archive для archived и complete для done без нового `--commit` — no-op с кодом 0, без записи/новой истории. Повтор complete с новым доказательством для done — ошибка: история не переписывается. Resume для active — ошибка с сообщением, что задача уже запущена; start не используется для продолжения. Другие переходы, не перечисленные выше, запрещены. Edit/move не меняют статус.

`attach <branch> --id <id>` принимает только todo и существующую локальную ветку, отличную от target_branch, без текущей связи другой задачи. Не делает checkout, допускает dirty tree при отсутствии незавершённой Git-операции. Начинает новый active_attempt и фиксирует исходные локальные наблюдения; уже интегрированная до attach ветка сама по себе не закрывает задачу. Для done нужно start --again, attach не является обходом.

`attach ... --rebind` допустим для active/paused: явная замена связи с сохранением ID подхода, исходной ветки и истории перепривязок. Повтор той же подтверждённой связи — no-op. Чужая занятая ветка и target_branch запрещены. Старое tracking-доказательство не переносится автоматически: новые наблюдения требуют проверки. Сходство SHA не считается переименованием. При resume отсутствующая ветка требует явного rebind, без случайного checkout.

`complete` разрешён для todo/active/paused. Показывает ID/title и основание manual, требует подтверждения или `--yes`. Без active_attempt создаёт завершённую ручную запись с новым ID; с active_attempt переносит именно его в attempts. `--commit` — необязательная явная ссылка на существующий локальный commit, достижимый из текущего target_branch. Пользователь подтверждает связь с задачей; достижимость не меняет source на merge. Отсутствующий/недостижимый commit — ошибка без записи. Без `--commit` можно явно завершить задачу без Git-доказательств; никаких выдуманных SHA/ветки/начала работы. Это общий ручной переход, не отдельный режим squash.

До первого завершения `attempts` отсутствует, не `[]` и не `null`. Любой done содержит непустой attempts. Завершение одним сохранением меняет статус, добавляет завершённый подход и удаляет active_attempt. Повторное событие дедуплицируется по ID подхода, а не только SHA. Повторный start сохраняет прошлые записи; новое завершение дописывает одну запись. Наличие attempts означает «завершалась раньше», а не обязательно текущий done.

Основания завершения: `merge` (обычный или fast-forward с отдельным видом доказательства), `manual`, `imported`. Реальные времена записываются отдельно от времени обнаружения; неизвестные поля отсутствуют. ID задачи/подхода/события не вычисляются только из времени. Точные JSON-поля, version и validation оформляются P03/P05; эти инварианты обязательны для схемы.

Формат схемы 1, доменные типы и правила валидации описаны в [MODEL.md](MODEL.md).
Проверка структуры Git-доказательств в модели не заменяет проверку их истинности tracking.

## 6. Порядок и вставка

Полный явный массив порядка содержит каждый ID ровно один раз, включая archived. Чтение не сортирует его заново. ID и отображаемый номер стабильны, не равны позиции. Автоматический start и «следующая» в status используют один первый todo.

Завершения получают монотонный локальный порядковый номер события при записи под блокировкой. Он задаёт порядок зарегистрированных завершений при совпадающих/ненадёжных часах. «Последнее по времени» в интерфейсе — последнее зарегистрированное завершение, а не максимальная дата commit. При sync, одновременно обнаружившем несколько завершений с неизвестной взаимной хронологией, события назначаются в текущем порядке задач; последняя из них становится опорой. Не утверждать, что это исторический порядок работы человека.

После каждого нового события завершения опора будущих вставок — завершённая задача, хвост группы — она же. Обычный add/start --new вставляет сразу после хвоста и делает новый пункт хвостом. Без событий используется виртуальная опора перед первым пунктом. Несколько добавлений следуют в порядке вызовов. При создании пустого плана хвоста ещё нет.

Markdown-импорт сохраняет входной порядок целиком. Его [x] получают события imported в порядке строк, без придуманных дат; последняя [x] — опора, начальный хвост равен ей. Если [x] нет, импортированные задачи образуют начальную группу, хвост — последняя из них: последующий add дописывается в её конец. JSON-импорт сохраняет уже существующую хронологию и хвост как часть данных. Это детерминированный fallback для отсутствующих дат, не восстановление реальной хронологии.

Явные add --after/--before/--end не сдвигают автоматический хвост. Move сохраняет хвост по ID: если сам хвост переместили, следующее автоматическое добавление следует за ним в его новом месте. Завершение другой задачи сбрасывает хвост на новую опору и не перемещает старые пункты. Archive и start --again опорной задачи не стирают событие/хвост; они не являются новым завершением. Задачи физически не удаляются. Хвост/номер события сохраняются в плане между процессами.

| Операции | Итоговый порядок |
|---|---|
| Пусто → add A → add B | A, B |
| Импорт todo A,B → add X → add Y | A, B, X, Y |
| A,B,C; complete A → add X → add Y | A, X, Y, B, C |
| Предыдущая строка → complete C → add Z | A, X, Y, B, C, Z |
| Импорт A[x],B[ ],C[x],D[ ] → add X → add Y | A, B, C, X, Y, D |
| A[x],X,Y,B; хвост Y → move Y --end → add Z | A, X, B, Y, Z |
| A[x],B; хвост A → add E --end → add X | A, X, B, E |

## 7. Хранение, init и редактирование

В plan.json находятся маркер формата, версия схемы/ревизия, target_branch, порядок, задачи и метаданные порядка событий. Локальные backup/lock/журнал/временные файлы допустимы только как обслуживание единственного плана. Не создавать config.json, tasks/<id>.json, служебные refs/коммиты или менять `.gitignore` ради хранения.

Init вычисляет корень, Git directory/common directory и `info/exclude` через Git. Добавляет отдельную строку `/.git-task/` с сохранением существующих байтов/записей и корректной границей строки. Повтор init с тем же target — no-op, кроме восстановления отсутствующего собственного исключения. С другим `--target` — ошибка, не скрытая перенастройка. Init допускается в unborn repo: сохраняет имя цели, предупреждает об отсутствии commit; start требует существующего основания. Default `main` не заменяется текущей веткой; для master нужен явный `--target master`.

Чужой `.git-task/`, неизвестный/повреждённый plan.json, symlink/junction служебного пути, tracked `.git-task/` в индексе/HEAD — отказ без перезаписи. Существующий пустой обычный каталог допускается; непустой принимается только как распознанное собственное хранилище или диагностируется. Не выполнять `git rm --cached`. Перед собственным переключением проверять и целевое дерево: Git-ignore не защищает уже отслеживаемые файлы. [Официальный gitignore](https://git-scm.com/docs/gitignore), [определение путей через rev-parse](https://git-scm.com/docs/git-rev-parse).

Init затрагивает два файла, поэтому не обещает общую файловую атомарность: если exclude успешно дополнен, а создание плана прервалось, повтор безопасно завершает init без дублирования строки. До проверки занятости/принадлежности путей не менять ни один из них. Отказ не должен оставлять валидный план, считающийся защищённым при неустановленном исключении. Проверяется фактическое действие исключения: если правила более высокого приоритета снова включают служебные файлы, init сообщает конфликт и не создаёт план; чужой .gitignore не исправляется автоматически.

Запись CLI/hooks: прочитать и валидировать; получить межпроцессную блокировку; перепроверить ревизию и исходное содержимое; построить и валидировать новое состояние; сохранить последнюю валидную предыдущую версию; записать временный файл на той же файловой системе; безопасно заменить основной файл и закрыть ресурсы с обработкой ошибок. No-op не меняет plan.json, backup и ревизию. При конфликте не применять автоматическое last-writer-wins. Точный механизм блокировки/замены и его гарантии на ОС определяет P05 с тестами сбоев.

Прямой редактор не соблюдает lock: сравнение содержимого обнаруживает многие, но не все гонки между последней проверкой и заменой. При обнаружении изменения/повреждения сохранять обе доступные версии, не затирать внешнюю правку. Чтение повреждённого JSON не подменяет его автоматически backup. Неизвестная новая схема — отказ; миграция известных старых схем должна быть явной и сохранять оригинал (реальные миграции — когда появится вторая схема).

Edit без полевых флагов открывает временный документ только title/description вне блокировки. Ненулевой выход редактора, невалидный документ и конфликт версии отменяют запись; неизменённый файл — no-op. Выбор редактора: GIT_EDITOR, core.editor, VISUAL, EDITOR; если ничего нет, диагностическая ошибка с предложением полевых флагов. Не подставлять title/description в shell-команду; правила разборки доверенной конфигурации редактора фиксируются и тестируются P11. Непринятый результат при конфликте сохраняется с указанным пользователю путём.

Формат документа, правила кавычек, приоритет настройки, коды ошибок и протокол resume описаны в [LIFECYCLE.md](LIFECYCLE.md). Настройка редактора запускается как программа с аргументами без shell; путь документа передаётся отдельно. Ненулевой выход редактора считается отменой (130), невозможность запуска — ошибкой (1).

Операции только над планом сохраняют HEAD, refs, индекс, staged/unstaged код и работают при dirty tree. Прямое изменение структурных полей JSON допускается лишь при соблюдении схемы; конфликт с текущими связями отклоняется. Смена target_branch при наличии active/paused запрещена, история хранит цель своего завершения.

## 8. Импорт и экспорт

Markdown — UTF-8 (допускается BOM), LF/CRLF. Поддерживается плоский список строк `- [ ] title`, `- [x] title`, `- [X] title` без отступа; пробельные строки и ATX-заголовки `# ...` вне списка игнорируются. Один пробел после `]` отделяет title, остаток сохраняется буквально. Прочий текст, вложенность, продолжения пунктов, блоки кода, другие маркеры и пустой title дают ошибку с номером строки; вложенные пункты не разворачиваются молча. Файл без пунктов — ошибка. Одинаковые title допустимы и получают разные ID/номера.

Сначала прочитать и проверить весь документ и пустоту назначения, затем показать количество, порядок, статусы, формат и цель назначения. Интерактивное подтверждение по умолчанию — «нет»; `--yes` разрешает применение без терминала после той же проверки. Предпросмотр/отмена не меняют план. Перед единственной записью повторно проверить пустоту и версию. Непустой план, в том числе состоящий только из archived, не очищается и не дополняется импортом. `--yes` не разрешает перезапись.

`[ ]` создаёт todo без attempts. `[x]`/`[X]` создают done с одной записью imported; фактические дата завершения, ветка, SHA и начало неизвестны и отсутствуют. Время импорта может быть записано как время наблюдения. Файл-источник не редактируется и не синхронизируется после импорта.

Markdown-экспорт — представление для чтения: все задачи в полном порядке, `[x]` только для текущего done, `[ ]` для остальных; ID, description, связи, история и различие paused/archived/active не переносятся этим форматом. Предупреждение о потерях идёт в stderr. Если title содержит перевод строки и не представим одной строкой, экспорт markdown отказывает с предложением JSON, не меняя title.

Полный JSON — версионированный снимок канонических данных плана, сохраняющий ID, номера, порядок, состояния, active_attempt, attempts, настройки и хронологию вставок. Lock, pending-operation, временные пути, кеши и установленность hooks не экспортируются. Схема P03/P05 будет общей с файлом хранения; JSON-экспорт доступен только для валидного согласованного плана. JSON-импорт в пустой план принимает настройки снимка (показывает их в предпросмотре), проверяет версию, ID, ссылки и инварианты. Не меняет refs и не создаёт ветки. Сохранённые наблюдения нельзя считать свежим доказательством в окружении назначения: sync перепроверяет их локально. Это не реализация P13.

Export не переписывает существующий путь, файл источника и собственные служебные файлы. Ошибка записи не выдаётся за успех. Полный экспорт при незавершённой операции отказывает до восстановления; doctor позволяет отдельно сохранить доступные исходные данные для разбора. Удаление `.git-task/`, например внешней очисткой игнорируемых файлов, может удалить и backup; отдельный пользовательский экспорт полезен для резервирования.

## 9. Tracking, sync и возвращение к проекту

Одна операция сверки обслуживает sync/status/hooks. Она работает с active и paused. Неполные доказательства — предупреждение, исходный статус сохраняется. Archived и завершённые attempts не используются как текущая работа. После доказанного done удаление/переписывание ветки не отменяет историческое завершение автоматически; при обнаружении потери достижимости доказательства показывается предупреждение.

Для автоматического done одновременно нужны:

1. Достоверная связь с текущим ID подхода; начальное основание и целевая ветка известны.
2. Свидетельство работы текущего подхода, реально находившейся вне целевой истории. Достижимость стартового commit, пустая ветка и одно только подтягивание main не являются работой задачи.
3. Проверенный актуальный tip этой работы и его интеграция в текущую target_branch обычным merge/fast-forward. Не применять сохранённый старый tip после обнаруженного продолжения, reset/rebase/amend, удаления или пересоздания ветки.
4. Достаточные локальные объекты/история и отсутствие противоречивых наблюдений. Ошибка Git не является отрицательным результатом ancestry и тем более доказательством завершения.

Обычный merge/fast-forward при наблюдённой собственной работе закрывает задачу без вопросов. Если post-merge пропущен, сохранённые наблюдения о работе плюс неизменённая подтверждённая связь и текущая история позволяют sync/status завершить задачу. Если пропущены все наблюдения, допускается восстановление из достаточных локальных Git-свидетельств; если отличить работу от простого обновления main нельзя, результат — неопределённость. Сама по себе пара «ветка достижима из main» недостаточна. P09 обязан описать конкретные достаточные доказательства в TRACKING.md и проверить графы настоящим Git.

Удалённая ветка, неоднозначное переименование/пересоздание и устаревшее наблюдение не закрывают незавершённую задачу по старому SHA; требуется достоверное восстановление связи/наблюдений. Консервативный результат при недостатке данных — предупреждение и сохранение статуса. Локальные наблюдения не являются полным аудитом произвольных внешних операций; невозможно обещать распознавание любой незаписанной подмены ветки.

Squash/cherry-pick, совпадение patch/tree и неоднозначное переписывание не дают автоматического done. Merge в другую ветку тоже не закрывает задачу до доказанной интеграции в target_branch. При незавершённом конфликте слияния/rebase сверка не финализирует подходы; после разрешения и commit сверяет снова. Нет эвристики по commit message или автору.

Git проверяет ancestry кодами 0/1, а иные ошибки отличает отдельно; squash не записывает обычную merge-связь. Правила завершения выше — выводы продукта из этих ограничений, не обещание Git распознавать задачи. [merge-base](https://git-scm.com/docs/git-merge-base), [merge](https://git-scm.com/docs/git-merge).

Status показывает в таком порядке: цель и текущая ветка/связанный ID (либо detached), прогресс, active/paused в порядке плана, последнее зарегистрированное завершение, первый todo, предупреждения/следующие действия. Показывает все активные задачи, а не только задачу HEAD. Прогресс = количество текущих done / количество не archived; при знаменателе 0 — «0 из 0, процент не определён», без деления на ноль. Повторно начатая задача больше не входит в числитель. Последнее завершение может относиться к уже начатой заново/архивированной задаче, что явно подписывается.

Show содержит id, number, title, description, статус, active_attempt отдельно от attempts, ветку/цель, известные commit ID, источник завершения и предупреждения. Commit time подписывается как время Git-коммита, не как точное время последней работы человека.

`status --json` имеет собственную `schema_version: 1`, поля `repository`, `progress`, `tasks`, `current_task_id`, `last_completion`, `next_task_id`, `warnings`. Tasks идут в полном порядке, включая archived; отсутствующие текущая/следующая задача и последнее завершение — null. Progress содержит done/total и percent=null при total=0, иначе 100*done/total с округлением до одного десятичного знака. Warnings — объекты со стабильным code, message и при необходимости task_id. Точная вложенная схема и примеры: [STATUS.md](STATUS.md). Новые необязательные поля допускаются, изменение смысла/типа существующих требует новой версии.

Сверка может сохранять новые наблюдения/завершения. Неизменившийся status/sync не переписывает файл: время запуска само по себе не новое наблюдение. Во время незавершённой операции status выводит последний согласованный план и предупреждение без автоматического repair.

## 10. Hooks, ошибки и восстановление

Во время обычного post-merge Git может ещё хранить MERGE_HEAD уже завершённого merge. Только этот вход общей сверки допускает такой маркер после проверки родителей HEAD против ORIG_HEAD/MERGE_HEAD и равенства индекса дереву HEAD. Остальные маркеры незавершённых операций и конфликты блокируют done; проверка повторяется перед записью. Hook не удаляет состояние Git. Сам факт события не заменяет доказательств tracking, обычные sync/status сохраняют строгую проверку. Подробности — [HOOKS.md](HOOKS.md).

Hooks install подключает post-commit, post-merge, post-checkout, post-rewrite. Они передают события общей сверке, работают без вопросов/сети, с ограниченным ожиданием lock. Ошибка собственного обработчика предупреждает, не отменяет уже совершённый Git commit/checkout. Post-checkout способен вернуть ошибку после переключения; post-rewrite передаёт отображение старых/новых commit через stdin. Точные контракты, аргументы и коды сохраняются. [Официальные githooks](https://git-scm.com/docs/githooks).

Минимально поддерживается локальный каталог hooks: пустой слот либо обычный существующий исполняемый hook, который можно сохранить и вызвать ровно один раз с прежними аргументами, cwd, окружением и stdin. Чужой обработчик выполняется первым, затем собственный; собственный сбой не меняет код чужого. Для post-rewrite входные данные должны достаться обоим. P10 проверяет эту цепочку реальными Git-тестами на ОС. Существующие менеджеры/неизвестные обёртки и общий внешний core.hooksPath не изменяются автоматически: диагностика и инструкция ручного подключения. Symlink/неизвестный тип hook — такой же отказ. Сам install не меняет глобальные настройки.

Установленные компоненты имеют маркер принадлежности/контроль исходного содержимого. Повтор install — no-op, uninstall удаляет только неизменённую собственную обёртку и восстанавливает сохранённый чужой hook. Изменённая после установки обёртка сохраняется с диагностикой. Plan/backup/ветки при uninstall не удаляются. Отсутствующий бинарник в hook предупреждает и не ломает чужой hook. Без установки hooks sync остаётся рабочим.

Конкретная граница автоматической цепочки P10: свободный слот либо обычный LF-shell-hook с точным `#!/bin/sh` в каталоге внутри Git-dir. Другие интерпретаторы, неизвестные обёртки/менеджеры и пути наружу требуют ручного подключения. Файлы, читающие собственный исходник, также подключаются вручную. При ошибке ресурсов полного копирования stdin post-rewrite не обещается: выводится диагностика. Протокол установки, входные данные, прерывания и инструкции — [HOOKS.md](HOOKS.md).

| Ситуация | Поведение |
|---|---|
| Не Git-репозиторий / Git отсутствует | Команды плана отказывают до записи; help/version доступны; doctor сообщает причину |
| Unborn, нет commit | init/add/import/edit/move/просмотр допустимы; start/attach/resume и complete --commit отказывают; цель не подменяется HEAD |
| Detached HEAD | Просмотр/плановые изменения/сверка допустимы; start/resume отказывают с просьбой сначала явно выбрать ветку; attach не переключает HEAD |
| Незавершённый merge/rebase/cherry-pick/revert/am или unmerged index | start/attach/resume/rebind/complete отказывают; status/sync сообщают состояние без финализации; add/edit/move/pause/archive допускаются как чистые изменения плана |
| Dirty tree | Только операции переключения start/resume блокируются; другие разрешённые операции сохраняют индекс и код |
| Нет target_branch / ветки подхода / Git-объекта | Предупреждение сверки без done; start без доступного основания отказывает; отсутствующая цель всегда блокирует start, даже с --from |
| Bare, shallow, partial clone, дополнительные worktree | Отказ операций плана без мутаций/сети; doctor объясняет неподдерживаемую конфигурацию |
| Повреждённый/чужой/неизвестный формат, внешний конфликт | Ошибка без перезаписи; doctor показывает безопасное следующее действие |
| Недоступная запись/backup/lock | Ненулевой код; сохранить старую версию или диагностируемый путь восстановления, не сообщать фиктивный успех |
| Прерванный start / resume | Сверка журнала с фактическим Git, без слепого повтора; состояние до/после объясняется пользователю |

Doctor по умолчанию только читает: Git/версию и окружение, корень/common directory, target, формат/инварианты, exclude, hooks, текущие связи, pending-operation, lock и backup. Каждый найденный дефект имеет следующее действие. Он не снимает lock по одному возрасту и не восстанавливает backup при обычном чтении.

`doctor --repair recover-start` обслуживает start и переключение resume. Показывает ID операции, журнал, результат сравнения плана и фактическую ветку/HEAD. После подтверждения под межпроцессной блокировкой повторно проверяет журнал, ревизию/содержимое плана и Git-состояние. Различает следующие случаи:

| Состояние | Допустимое восстановление |
|---|---|
| План совпадает с исходным снимком; Git-эффект намерения подтверждён, владение операцией установлено | Подготовить результат по сохранённому намерению и подтверждённым фактам, сохранить его проверяемое описание в журнале по §4.2, затем однократно записать план и закрыть журнал. Для --new отсутствие задачи в исходном плане ожидаемо; для resume используется прежний подход |
| План совпадает с исходным снимком; подтверждено отсутствие Git-эффекта | Закрыть намерение без эффекта, сохранив план и Git как есть; не запускать операцию заново |
| План совпадает с подготовленным результатом именно этой операции, включая ревизию и полное содержимое/отпечаток; её Git-эффект и владение подтверждены | Результат уже применён: закрыть только журнал. Не повторять Git, запись plan.json, создание задачи/подхода, изменение attempts, ревизии или backup |
| План не равен исходному и не совпадает с доказанным подготовленным результатом (в том числе его описание отсутствует/повреждено); либо нарушена целостность намерения, изменился журнал, Git-состояние противоречиво/неопределённо | Отказ, сохранение плана, Git и журнала для явного разбора. Совпавший active_attempt при последующей внешней правке title/другой задачи не разрешает закрыть журнал |

Таким образом, проверка «исходное состояние не изменилось» относится только к ещё не сохранённому результату; ожидаемое изменение собственной операцией не считается посторонней правкой. Восстановление не удаляет ветку и не переключает её силой. Если repair сам прерывается после записи плана, следующий repair распознаёт уже применённый результат и выполняет только закрытие журнала. Ошибка закрытия журнала даёт ненулевой код с сообщением, что план уже сохранён; план не откатывается. При повторном repair после успешного закрытия, когда незавершённого журнала нет, результат — код 0 и «Нет незавершённой операции», без записи, Git-мутаций и запроса подтверждения. Закрывать можно только проверенный журнал с тем же ID; появившееся другое намерение требует новой диагностики.

`doctor --repair restore-backup` сначала проверяет копию и сохраняет повреждённый оригинал отдельным файлом, показывает отличия/возраст, затем после подтверждения восстанавливает с проверкой версии. Backup не переносится поверх активной операции. `doctor --repair unlock` требует доказательства отсутствия владельца/операции, возраста недостаточно. При невозможности проверить владельца отказывает. `--yes` заменяет только подтверждение, не проверки.

Конкретный протокол: [DOCTOR.md](DOCTOR.md). Предпросмотр не пишет файлы;
после подтверждения оригинал сохраняется до замены. Это уточняет порядок
предыдущего абзаца: отмена подтверждения не оставляет новых служебных файлов.
Выбор restore-backup явно предупреждает о возможной более свежей очереди
в повреждённом оригинале. Валидный план, чужой формат и распознаваемая
несовместимая схема не заменяются. Публикация прежних ID возобновляется
через `team publish`; doctor без repair не выполняет сеть и не применяет
полученный снимок. Последняя ошибка транспорта не хранится отдельно:
показываются очередь и отсутствие подтверждения, без выдуманной причины.

Repair с изменениями всегда показывает предполагаемые действия и требует подтверждения; автоматического reset/stash/удаления ветки/принудительного снятия lock нет. При отсутствии валидной копии допускается сохранение доступных сырых данных для разбора, но не объявление их валидным JSON-экспортом.

## 11. Действующий контракт: общий план и параллельные подходы

Решение пользователя 2026-10-04 заменяет прежние правила единственного active_attempt, появления attempts только при done и запрета служебной ветки. Требования, прогресс и фактическая независимая приёмка P13 имеют один источник — [PLAN.md](../PLAN.md); здесь контрактные последствия принятой реализации.

### 11.1. Модель и миграция

Схема 2 хранит все подходы задачи в attempts. Каждый новый связанный подход имеет устойчивый ID, author, started_at, branch/target_branch и status active/paused/done. Completion обязателен для done и не выдаёт manual/imported за merge. Неизвестные автор/время старых или импортированных записей остаются неизвестными; нельзя приписать историю мигрирующему пользователю. Миграция сохраняет прежние ID/историю, исходник/backup и обнаруживает прерывание; неизвестные версии отклоняются. Локальные observation и ссылки operation-журналов не становятся достоверными общими данными другого clone.

Для неархивной задачи без подходов — todo; непустой набор всех done — done; при наличии active — active; иначе незавершённые paused дают paused. Archive сохраняет подходы и замораживает задачу без фиктивного завершения. Поздний offline-подход автоматически может вернуть done в active; это допустимо, пользователь уведомляется. Пока online-регистрация не обязательна, учитываются все известные подходы.

ID не меняется при merge/публикации/перестановке и не зависит от часов. Принятая операция start уже генерирует 16 случайных байт; сохранить этот принцип для новых подходов/действий и обеспечить устойчивую идентичность новых задач при offline-add. Старые task IDs мигрируют без перенумерации. Видимые последовательные номера отделены от ID; одинаковое имя автора не объединяет разные подходы. Конкретное представление автора оформляется в схеме/help; author — атрибуция, не ACL/аутентификация.

### 11.2. Команды и подходы

Обычный start сохраняет обязательное имя ветки, автоматический первый todo и точные --id/--title. Явное начало active/paused-задачи может добавить отдельный подход; done требует --again. Resume продолжает существующий paused-подход. Ручные switch -c/checkout -b/branch не создают связи. Pause/resume/complete/rebind принимают --attempt по точному ID; без него выбирается только единственный локально связанный незавершённый подход. Неоднозначность даёт ошибку; чужой/первый подход молча не выбирается, hooks не спрашивают. Автоматический tracking завершает только подход с собственным доказательством; повтор сохраняет ID без дубля.

### 11.3. Хранение и обмен

Локальная рабочая копия имеет один игнорируемый .git-task/plan.json при всех checkout веток кода. Общая копия plan.json отслеживается только в отдельной git-task-plan того же remote, с собственной историей без кода; она не вливается в target_branch. Плагин управляет локальной служебной веткой/remote-tracking ref без изменения рабочего индекса/истории кода. Target_branch — цель завершения, не запрет правок из feature. Подключение/выбор remote явны и не перезаписывают чужую ветку или данные.

Публикация в подключённом командном режиме: получить свежую служебную версию, согласовать с общей базой и локальными действиями, валидировать, создать обычное fast-forward обновление. Сеть выполняется вне storage-lock; локальный снимок проверяется после неё. Конкурирующее серверное обновление приводит к отказу устаревшего push и ограниченному повтору после fetch; force/reset запрещены. Объединение выполняет плагин, не стандартный Git-сервер и не текстовый merge JSON.

Разные IDs attempts сохраняются автоматически с уведомлением о параллельной работе. Повтор того же действия не создаёт дубля; одинаковый ID с несовместимыми данными требует диагностики. Старое active не отменяет done того же подхода: учитывать базу/действие. Очередь сохраняет start, add, complete и остальные неопубликованные мутации, даже без ветки или после её интеграции. При сети/авторизации/lost-ack не уничтожать план/ветку/очередь, не сообщать о подтверждённой публикации без основания. Неопубликованное действие и незавершённая локальная Git-операция различаются.

### 11.4. Hooks и границы доставки

Стандартного post-pull нет. Получение новой версии отмечать по изменению служебной remote-tracking ссылки через reference-transaction или доказанный эквивалент. Hook не выполняет сеть и не мешает чужим hooks; fetch может идти до интеграции кода. Применение плана и tracking используют безопасные фазы/локальные locks. Проверить merge/rebase/fast-forward/no-op кода/конфликт и восстановление пропущенного события. Появление интернета без Git/CLI-команды ничего не запускает.

Локальные hooks могут поставить завершение в очередь; публикация выполняется при следующем сетевом сценарии приложения. Server-side merge не вызывает hook машины разработчика. Для управляемого Git-сервера реализован вход team reconcile и пример post-receive с отдельным полным clone-worker: событие target before/after сохраняется, сверка проверяет доступные ссылки подходов и публикует доказанные завершения. Установка и права описаны в P13-IMPLEMENTATION; изолированные результаты — в PLAN. Внешний deployment требует отдельной авторизации и не выполнен. Хостинг без доступа к hooks требует отдельной интеграции, готовый универсальный SaaS-trigger не обещается. Локальные status/sync остаются без сети. Автоматическое создание/публикация веток кода и решение одинаковых имён не включены в P13. Отсутствие ветки не доказывает done чужого подхода.

### 11.5. Отложенные решения

TODO-01–04 имеют один источник прогресса в PLAN.md и раскрыты с владельцами решений в [ROADMAP.md](ROADMAP.md): усиленный readback/обязательная online-регистрация; права ручного редактирования; полная политика несовместимых title/order/archive/add; отложенные среды. До реализации прав author не является защитой. До resolver несовместимые ручные правки обнаруживаются и сохраняются обеими сторонами, без молчаливой перезаписи. Эти расширения не блокируют базовое объединение независимых подходов.

## 12. Реализованный интерфейс схемы 2

Схема 2, очередь, селектор подхода и выбранный серверный запуск описаны в [P13-IMPLEMENTATION.md](P13-IMPLEMENTATION.md). Команды: migrate; team connect --remote <name>; team fetch; team publish; team reconcile [--before <oid> --after <oid>]. Pause/resume/complete и attach --rebind принимают --attempt <точный ID>. Без селектора подхода допускается только один подход этого clone. Новая явная start/attach к active/paused добавляет отдельный подход; done требует start --again.

Предыдущие разделы со схемой 1 описывают принятые P01–P12; действующая схема 2 заменяет active_attempt общим массивом attempts и агрегированным статусом. Author неизвестной истории не выдумывается. Импорт/экспорт JSON очищает локальные настройки, наблюдения и очередь. Status JSON имеет отдельную версию 2. Серверная автоматизация — post-receive с изолированным worker на Git-сервере, допускающем hooks; установка на внешний сервер не выполнена. Фактические независимые проверки и следующая роль находятся только в PLAN.md; финальная передача — [HANDOFF.md](HANDOFF.md).
