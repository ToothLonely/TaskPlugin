# Локальное хранилище

## Контракт P05

Единственный источник данных — `.git-task/plan.json`. JSON использует модель
из MODEL.md: `format: "git-task"`, `schema_version: 1`, `revision`,
`target_branch`, `order`, `tasks`, `last_event`, необязательный `insertion_tail`.
Статусы: `todo`, `active`, `paused`, `done`, `archived`; активная попытка хранится
в `active_attempt`, завершённые — в `attempts`. Старое название активного
статуса больше не принимается. Это согласованное изменение формата до выпуска;
автоматической подмены произвольного пользовательского JSON нет.

Схема 1 — первая поддерживаемая. Декодирование отдельно проверяет маркер и
версию, затем все инварианты модели. Неизвестная версия отклоняется без записи.
При появлении схемы 2 миграция должна стать отдельной явной операцией: чтение
старым декодером, преобразование, валидация новым и сохранение исходных байтов.
Фиктивная миграция из несуществующей схемы 0 не вводится.

## До записи

Git определяет корень и info/exclude. Операции отказывают для bare, shallow,
partial clone и дополнительных worktree. Проверяется `.git-task` и в индексе,
и в HEAD; удалённый из индекса, но ещё присутствующий в HEAD путь тоже занят.
Проверка учитывает фактическую чувствительность файловой системы к регистру:
`.GIT-TASK`/`.Git-Task`, обозначающие тот же каталог, тоже запрещены. Для
существующих путей сравнивается файловая идентичность; если оба написания
отсутствуют, проверяется поиск другого существующего имени в том же родителе
без создания пробных файлов. Разные физические каталоги на чувствительной
к регистру файловой системе не отождествляются. Настройка `core.ignoreCase`
не является доказательством свойств файловой системы.
Каталог, файлы данных и служебные пути не могут быть symlink/junction.
Чужой непустой каталог, повреждённый план и неизвестная схема сохраняются.

Init сначала проверяет пути, затем получает `write.lock` через эксклюзивное
создание файла. Существующая блокировка означает отказ; возраст не разрешает
её снять. Файл содержит маркер, PID и время для диагностики. После аварийного
завершения он остаётся: восстановление требует проверки владельца; автоматический
unlock и doctor относятся к P14. Чтение при блокировке отказывает с диагностикой.

Init сохраняет байты чужого info/exclude и дописывает отдельную строку
`/.git-task/`. Перед созданием плана Git проверяет фактическое игнорирование
каталога. Переопределяющий `.gitignore` даёт ошибку без создания плана.
Два файла init не образуют общую атомарную транзакцию: повтор безопасно
продолжает после добавления exclude. Смена target повторным init запрещена.

## Запись и восстановление

Чтение возвращает план и неизменяемый исходный снимок байтов. Save получает
блокировку, повторяет проверки Git/путей и сравнивает исходные байты; изменение
даже пробелов считается внешней правкой. Изменённый план должен иметь большую
ревизию и пройти полную валидацию. Равное содержимое модели — no-op без изменения
plan.json, backup и ревизии.

Перед заменой записывается и синхронизируется временный файл, затем предыдущий
валидный оригинал сохраняется как `plan.backup.json` через временный файл и
замену. Повреждённый существующий backup не затирается. Перед заменой плана
повторно сравниваются байты. Обнаруженный конфликт сохраняет подготовленный
результат в отдельном `pending-*.json`, указывая путь в ошибке.

Замена выполняется через os.Rename в том же каталоге, без удаления оригинала
перед ней. Первое создание использует hard link готового временного файла,
чтобы не перезаписать внезапно появившийся plan.json. Ошибки write/sync/close/
rename возвращаются; при сбое остаётся прежний план либо валидный backup и
подготовленный файл. Обычное чтение никогда не восстанавливает backup само.
Оставшиеся pending-файлы диагностируются и блокируют новые записи до разбора.

Это защита от кооперативных CLI-процессов и обнаруженных внешних изменений,
не от любого внешнего редактора между последней проверкой и заменой.
Одинаковая атомарность и устойчивость к отключению питания на всех файловых
системах не обещаются: Go отдельно ограничивает гарантии Rename вне Unix.
Матрица Windows/Linux/macOS подтверждается фактическими тестами P15/P17.

## Команды

P05 подключает `init [--target branch]`, `add title [--description text]
[--after id / --before id / --end]` и текстовый `status`. Status показывает
сохранённый порядок, ID, названия и состояния; tracking и JSON-представление
экрана возвращения относятся к P09/P12. Изменения модели передаются через Save;
интерактивный edit относится к P11.

Пример использования из каталога репозитория или его подкаталога:

~~~text
git task init --target main
git task add "Добавить профиль" --description "Форма и сохранение"
git task add "Подготовить API" --before task-001
git task status
~~~

Для запуска локальной сборки на Windows вместо `git task` можно указать путь
к `bin/git-task.exe`. Команда start остаётся отдельным этапом P06.
