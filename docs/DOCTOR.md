# Диагностика и восстановление

`git task doctor` только читает локальные данные. Он не вызывает status/sync,
не применяет полученную общую версию, не выполняет сеть, не создаёт lock.
Код 1 означает найденную проблему; неопубликованные действия сами по себе
нормальны. После offline, lost-ack, отмены или лимита публикации используйте
`git task team publish`: прежние ID сверяются со свежей базой. Повторять start
или complete ради публикации нельзя. Последняя ошибка транспорта не хранится:
doctor показывает очередь и отсутствие подтверждения, а не придумывает причину.

Operation-журнал разбирается из одного прочитанного снимка. Если его закрыли,
заменили или изменили план во время диагностики, doctor сообщает о смене
состояния и предлагает повторить чтение; он не блокирует writer и не делает repair.
Диагностика hooks собирается в CLI и передаётся app как функция чтения с
context и корнем репозитория. Логика проверки hooks остаётся в hooks.

Ремонты сначала показывают доказательства, затем требуют терминальное
подтверждение или `--yes`. Подтверждение не снимает проверки. Снимок файлов
повторно сравнивается под блокировкой; изменённое намерение требует нового
предпросмотра. Диалог проходит вне блокировки.

`doctor --repair recover-start` использует существующий журнал и проверку
фактического Git. Нет журнала — успешный no-op без подтверждения. Совпавший
результат закрывает только журнал; ветки не создаются, не удаляются и не
переключаются. Незавершённый журнал отличается от очереди публикации.

Если жёсткое завершение оставило write.lock вместе с operation.json,
recover-start допускает обслуживание только валидного неизменённого журнала
при доказанном отсутствии распознанного владельца этого компьютера. Под
recovery-lock заброшенный lock заменяется собственным lock; затем выполняется
обычная проверка Git и журнала. Живой или неизвестный владелец блокирует ремонт.
Отказ проверки Git сохраняет журнал; ветки и план не меняются.

`doctor --repair restore-backup` допускается только для повреждённого плана
с валидным backup схемы 2, без operation и остатков pending-записи. Валидный
план, чужой формат и известная несовместимая схема не заменяются. Оригинал
сначала сохраняется в `conflict-original-*.json` и синхронизируется на диск;
backup остаётся неизменным. Кандидат устанавливается безопасной заменой с
повторной проверкой обоих снимков. При сбое сохранённые кандидаты не удаляются.
Предпросмотр показывает возраст, размер, ревизию backup и предупреждает:
нечитаемый оригинал может содержать более свежую очередь. Явное подтверждение
этого действия означает выбор старого снимка; исходные байты остаются для
отдельного разбора, автоматическое восстановление повреждённой очереди невозможно.
Backup содержит собственную очередь, базу и устойчивые ID; она продолжает
публиковаться обычным team publish.

`doctor --repair unlock` снимает только распознанный lock этого компьютера,
если ОС доказала отсутствие PID и нет operation/pending. Возраст недостаточен;
старый формат без имени компьютера, чужой компьютер, отказ доступа или живой
PID (включая повторное использование PID) означают отказ. Новый lock содержит
hostname. Перед удалением проверяются байты и идентичность файла. Параллельные
unlock сериализуются отдельным recovery-lock; обычный writer проверяет его
до и после получения своего lock. Прерванный recovery-lock требует ручного
разбора и не снимается этим действием.

Bare, shallow, partial clone и дополнительные worktree не ремонтируются.
Для них doctor объясняет ограничение до мутаций. Неизвестные схемы, повреждения
общего снимка/базы/очереди и неподдерживаемые hooks требуют сохранения исходников
и отдельного разбора. Force push и изменения истории кода не применяются.
Внешний редактор и произвольный Git-процесс не соблюдают lock: сравнение снимков
обнаруживает наблюдаемые изменения, но не гарантирует защиту от любой внешней гонки.
