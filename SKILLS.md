# Git Task — руководство по разработке на Go

Этот файл содержит проектные инструкции и маршруты работы. Прочитать его требует [AGENTS.md](AGENTS.md); задания и статусы находятся в [PLAN.md](PLAN.md). Это обычный документ проекта, не автоматически установленный пакет навыков.

Основная ветка разработки проекта — только `master`. Новый этап выполняется в отдельной ветке от актуальной локальной `master`; после успешного независимого ревью проверяющий коммитит изменения в ветку этапа и вливает её в локальную `master`. При исправлениях продолжается ветка этапа, при замечаниях слияние не выполняется. Подробный порядок определяет протокол PLAN.md. Имена веток пользовательских и изолированных тестовых репозиториев относятся к контракту продукта, а не к выбору основной ветки разработки проекта.

### Что смотреть в GitHub CLI

GitHub CLI описывает подмены внешних эффектов для своих тестов; наш tracking обязан дополнительно проверяться настоящим Git в изолированных репозиториях.

Копирование стороннего кода требует соблюдения его лицензии; по умолчанию реализовывать собственный небольшой вариант.

## Архитектура

Цель: новый разработчик по имени пакета и файла понимает, где искать нужное поведение. Ниже ориентир роста проекта, а не требование создать все папки на P02.

~~~text
cmd/
  git-task/
    main.go                 # запуск, код выхода, сборка зависимостей
internal/
  cli/
    root.go                 # диспетчеризация и help
    start.go                # аргументы/диалог команды start
    status.go               # вывод состояния
  app/
    start.go                # общий сценарий запуска задачи
    sync.go                 # согласование операций tracking и storage
  task/
    task.go                 # задачи, состояния и инварианты
    attempt.go              # попытки выполнения
    plan.go                 # порядок и операции над планом
  git/
    client.go               # исполнение процессов
    repository.go           # обнаружение репозитория и путей
    refs.go                 # типизированные операции со ссылками
  storage/
    store.go                # загрузка и сохранение метаданных
    schema.go               # формат, валидация, миграции
    transaction.go          # журнал/проверяемая запись
  tracking/
    observe.go              # наблюдения о работе
    completion.go           # решение о завершении и его доказательства
  hooks/
    install.go              # установка и удаление интеграции
    dispatch.go             # адаптация событий к общим операциям
  transfer/
    markdown.go             # формат пользовательского плана
    json.go                 # полный перенос состояния
tests/
  integration/              # только сквозные сценарии нескольких пакетов
docs/
go.mod
~~~

Названия дополнительных файлов выбираются по фактическим обязанностям. Tests рядом с кодом: task_test.go, completion_test.go и т. п. Testdata хранится рядом с потребляющими тестами. Общие тестовые помощники выделять после появления реального повторения.

### Границы и зависимости

| Пакет | За что отвечает | Чего в нём не должно быть |
|---|---|---|
| task | Доменные данные, переходы, порядок | os/exec, печать, JSON-файлы, terminal prompts |
| git | Выполнение Git и разбор стабильных форматов | Статусы задач, меню, принятие решения done |
| storage | Версии данных, чтение/запись, целостность | Пользовательское меню, форматирование status |
| tracking | Доказательства интеграции и неопределённости | Печать, самостоятельная сеть, скрытое изменение плана |
| transfer | Разбор/формирование обменных форматов | Самостоятельный checkout, изменение refs, сетевой transport |
| app | Последовательность действий, применение решений, координация хранения | Зависимость от cli или hooks, глобальные stdout/stderr |
| cli | Ввод, аргументы, представление | Повторная реализация доменных переходов и Git-транзакций |
| hooks | Установка обёрток, перевод событий | Дублирование sync, интерактивные вопросы |

Обычный путь: cli/hooks → app → task/tracking/storage/git. Storage работает с локальным JSON и task; обнаружение путей репозитория передаётся через узкую границу или подготовленные пути, ветки кода не используются для хранения плана; согласованный P13 хранит общую версию в отдельной git-task-plan через Git-адаптер; transfer — task; tracking — task и узкую границу чтения Git. Конкретные зависимости передавать через конструкторы/параметры. В app допустимы конкретные типы; интерфейсы нужны только там, где дают реальную подмену или отделяют контракт. App не импортирует cli/hooks: сборка интеграции выполняется снаружи, без цикла.

В P02 создаются только необходимые каркас и адаптер. App появляется, когда в P06/P09 нужно координировать многошаговую операцию для разных входов. Для маленького пакета допустим один файл. Разделять файл при появлении независимых ответственностей, а не после произвольного лимита строк.

### Для разработчика с Android-опытом

| Привычное понятие | Подход в этом проекте |
|---|---|
| Gradle-модули | Обычно один Go-модуль и несколько пакетов; пакет не требует своего go.mod |
| ViewModel / UI state | CLI разбирает ввод и выводит результат; lifecycle Android здесь отсутствует |
| UseCase | Функция или метод в app для настоящего сценария; отдельный тип на каждое действие не обязателен |
| Repository | Storage имеет явный контракт, но универсальный CRUD-слой ради названия не нужен |
| Hilt / DI | Конструкторы и параметры; граф небольших зависимостей виден в коде |
| Interface + Impl | Узкий интерфейс у потребителя при необходимости; конкретный тип достаточен по умолчанию |
| Exceptions / sealed Result | Обычные возвращаемые error и данные; типизированные ошибки для ветвления |
| Coroutine cancellation | context для отменяемого I/O; goroutine не нужна для каждой операции |

Это пояснение, а не указание буквально переносить Android-архитектуру.

## Идиоматичный Go

### Имена и API

Пакеты называются по смыслу, имена не дублируют имя пакета без необходимости. Exported-символы нужны только для использования другим пакетом; документируй их назначение и нетривиальный контракт. Не экспортируй всё ради тестов: подходящий пакет теста выбирать по тому, проверяется ли публичное поведение или локальный инвариант.

Интерфейсы обычно небольшие и принадлежат вызывающей стороне. Конструктор может возвращать конкретный тип. Pointer/value receiver выбирать по мутабельности, стоимости копирования и согласованности API, а не по правилу «все объекты — указатели». Типы с mutex нельзя копировать после начала использования. Ориентир: [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments).

Не создавать generics, reflection и цепочки functional options заранее. Простой struct с параметрами подходит, когда он действительно делает вызов яснее. Map не определяет порядок плана: порядок хранится явно. Не добавлять недетерминированность вывода обходом map.

### Ошибки и завершение

Ожидаемые проблемы пользователя и окружения возвращаются как error. Добавляй контекст операции один раз на полезной границе, а не одинаковый текст на каждом слое. Если вызывающий код должен узнать исходную причину, используй оборачивание и errors.Is/As. Не сравнивай текст ошибки для принятия бизнес-решения. Основа: [пакет errors](https://pkg.go.dev/errors).

Не печатай и не возвращай одну и ту же ошибку на каждом уровне: обычно итоговую диагностику формирует CLI. Ошибка записи/закрытия при сохранении данных существенна; ошибка cleanup оценивается по влиянию, а не игнорируется без причины. Fatal/Exit не должны обходить очистку внутри пакетов. Main завершает процесс после возврата функции run, где уже выполнены defer.

### Context и конкурентность

Context передаётся первым аргументом отменяемой операции; не хранится как бессрочное состояние объекта и не используется вместо явных параметров. Производный context освобождается вызовом cancel. Чистые переходы задач и парсеры не нуждаются в искусственном context. Основа: [документация context](https://pkg.go.dev/context).

Горутина требует владельца, условия завершения и способа дождаться результата. Сначала выбирать последовательный алгоритм, если требования не требуют конкурентности. Go mutex защищает память процесса, но не две отдельные CLI-команды: для plan.json нужны межпроцессная блокировка и проверка версии/содержимого, прочитанного до изменения. Держать блокировку во время пользовательского диалога или сетевого ожидания без необходимости нельзя.

## Команды и процессы

- Контракт start из PLAN.md обязателен: первый todo выбирается автоматически; --id выбирает точное поле id из JSON, --title — точный уникальный title. Number/позиция не являются ID; поиск заголовка не является созданием задачи. Оба селектора взаимоисключающие и поддерживают --again. Дубли title разрешены в плане, но неоднозначный поиск требует --id. Имя ветки обязательно как единственный позиционный аргумент во всех режимах; -b и автогенерации нет. Отсутствие имени/лишние аргументы отклоняются до меню и мутаций. Основание — target_branch; диалог только через --select.
- Отдельно: разбор аргументов, проверка запроса, операция app и представление результата. Флаги каждой команды разбирать собственным FlagSet; глобальный flag.CommandLine не превращать в изменяемое общее состояние тестов.
- stdin/stdout/stderr передаются явно; машинные результаты идут в stdout, диагностика — в stderr. JSON-режим не содержит ANSI и случайных строк от Git.
- Терминальный диалог не запускать при отсутствии интерактивной среды. EOF, отмена и неверный ввод — нормальные сценарии, не panic.
- Для Git использовать exec.CommandContext и отдельные аргументы; Cmd.Dir вместо глобального os.Chdir. Обрабатывая отмену, учитывать уже совершившиеся операции и возможные дочерние процессы hooks, не обещать автоматический откат.
- Различать отсутствие Git, код выполнения Git, отрицательную проверку и прерванную команду. Парсить stdout отдельно от stderr. Двоичные/NUL-разделённые данные не обрезать без разбора формата.
- Передача без shell не отменяет проверку опций: имя ветки не должно становиться --опасной-опцией. Использовать валидированные полные refs и разделители аргументов там, где это поддерживает конкретная команда.
- Для путей файловой системы — filepath; для Git refs и путей в Git-tree — соответствующие Git-правила. Не превращать имя refs/heads/feature/a в Windows-путь с обратными слешами.

Основа запуска процессов: [os/exec](https://pkg.go.dev/os/exec). Конкретные контракты Git проверять по документации используемой команды и реальным тестам.

## Git и сохранность данных

Перед реализацией мутации записать её инварианты и точки возможного отказа. Тест должен подтверждать фактические refs, индекс и рабочие файлы, а не только строку «успешно».

Локальный рабочий план — .git-task/plan.json; P13 добавляет общую отслеживаемую копию в git-task-plan и очередь неопубликованных действий. Не создавать файлы задач/настроек отдельно, не вливать metadata в ветки кода и не менять индекс/историю кода. Init сохраняет info/exclude. Общая база и очередь различаются с operation-журналом start; сетевое ожидание вне storage-lock, после сети повторная проверка снимка. Валидация/backup/безопасная замена и обнаружение внешних изменений сохраняются. No-op не переписывает файлы; повреждение или несовместимый merge не разрешает перезапись одной стороны.

Связь start и сохранение задачи — многошаговый сценарий. При ненулевом коде Git сначала выяснить, появилась ли ветка: сторонний post-checkout может вернуть ошибку уже после переключения. Восстановление опирается на журнал и фактическое состояние.

Для tracking важны доказательства именно текущей попытки. Начальный коммит пустой ветки уже может входить в целевую ветку. Сохранённый tip может устареть после новых коммитов, reset, rebase или повторного использования имени. При недостатке данных хранить неопределённость. Интеграция истории не доказывает смысловую корректность реализации.

Принятый P01–P12 использует схему 1 active_attempt/завершённые attempts. По решению 2026-10-04 P13 мигрирует к attempts со всеми подходами, author и отдельным status. ID сохраняются и не перенумеровываются по часам; независимые подходы автоматически объединяются, задача done после всех известных подходов done. Поздние offline-подходы могут вернуть active; done --again и честные manual/imported основания сохраняются. Lifecycle выбирает конкретный подход, tracking подтверждает только его собственную работу. Схема/правила — PLAN.md и целевой раздел SPEC, не старые исторические примеры.

Источники: [gitignore / локальные исключения](https://git-scm.com/docs/gitignore), [githooks](https://git-scm.com/docs/githooks), [merge-base](https://git-scm.com/docs/git-merge-base). Детальные требования и приёмка определяются этапами P05/P06/P09/P10/P13/P14 в PLAN.md. После явного возобновления P13 пользователем требования переноса применяются к выбранному и согласованному транспорту. Поддержка squash, включая отдельное ручное подтверждение, остаётся вне первой версии; не выдавать неподдерживаемый сценарий за автоматическое done.

## Проверки — обязательное условие завершения задания

Пользователь прямо требует: перед завершением задания агент пишет все необходимые тесты и запускает их. Это условие действует на каждом этапе изменения поведения, а не только на P15. P15 объединяет покрытие и CI, но не откладывает тестирование предыдущих этапов.

### Выбор необходимых тестов

| Изменение | Необходимое доказательство |
|---|---|
| Переходы задач/порядок | Первый todo, точные --id/--title, отсутствующий/неоднозначный title, конфликт селекторов; ошибка для done без --again и повторный запуск с любым селектором; сохранность attempts |
| Исправление ошибки | Регрессионный тест, который выявляет исходный дефект, когда это воспроизводимо |
| Парсер/импорт | Валидный ввод, повреждённый ввод, Unicode, границы и отсутствие частичной записи |
| CLI | Обязательное имя start, отказ без мутаций на отсутствие имени/-b/лишние аргументы; вывод, ошибки, код выхода; отмена и EOF для диалога |
| Git refs/merge/hooks | Интеграционные тесты с настоящим Git в изолированном репозитории |
| Хранение/восстановление | JSON и backup при сбоях, no-op/повторный init, сохранение info/exclude, отказ на чужой/tracked-путь, dirty tree и переключение веток; конкуренция записей |
| P13, общий план | Два настоящих clone/локальный bare remote, миграция/author/несколько attempts/все-done, offline/lost-ack/гонка публикации, fetch/pull и безопасные hooks; без credentials и внешней публикации |
| Только документация | Проверка полноты, ссылок, примеров и согласованности; искусственный Go-тест текста не нужен |

Тестировать поведение и инварианты, а не последовательность внутренних вызовов без контрактной причины. Table-driven tests подходят для вариантов одного правила; разные сценарии не обязательно объединять в огромную таблицу. Нужны понятные имена и диагностика фактического/ожидаемого результата.

Использовать t.TempDir, t.Cleanup и t.Helper по назначению. Не добавлять sleep для ожидания состояния, если возможна явная синхронизация. T.Parallel допустим только при действительно изолированном состоянии; смена окружения или cwd процесса требует особой осторожности. Основа: [testing](https://pkg.go.dev/testing).

Для Git-тестов задать собственные config, identity и каталог hooks; исключить влияние global/system config и унаследованных GIT_* указателей на чужой репозиторий. На Windows использовать реальный нужный Git, не предполагать Linux shell. Не менять окружение тестового процесса параллельно; по возможности задавать Env дочернему процессу. Сохранять сведения о версиях и кодах выхода для разбора сбоя.

### Порядок перед передачей на review

1. Связать новые/изменённые критерии с тестами и убедиться, что добавлены все необходимые сценарии, включая отказ и важные границы.
2. Отформатировать затронутый Go-код, запустить адресные тесты для быстрой проверки.
3. Перед готовой передачей изменения кода выполнить go vet ./..., go test ./... и go build ./... в существующем модуле. Не выдавать кешированный или прежний запуск за проверку более поздних изменений.
4. Для существенных изменений Git, hooks, восстановления и интеграционных тестов выполнить соответствующие тесты без кеша: go test -count=1 <packages>. На финальной приёмке запустить go test -count=1 ./....
5. Для новой/изменённой конкурентности выполнить go test -race на затронутых пакетах в поддерживаемой среде. Race detector не доказывает корректность межпроцессных блокировок: их проверять отдельными сценариями. [Race detector](https://go.dev/doc/articles/race_detector).
6. При изменении парсеров fuzzing уместен для сложных входов; при изменении зависимостей/подготовке релиза применять govulncheck в настроенной среде. Не устанавливать инструменты глобально без авторизации; наличие уязвимости оценивать по достижимости и исправлению. [Go Vulnerability Management](https://go.dev/doc/security/vuln/).
7. Записать команды, результаты, новые тесты и ограничения в журнал текущего этапа. После последнего исправления повторить затронутые проверки.

Если необходимые тесты не проходят или не могут быть запущены, нельзя переводить этап в review как готовый и объявлять задание выполненным. Сохранить active/changes_requested, а при внешнем препятствии — blocked по протоколу PLAN; перечислить точный сбой и следующее действие. Чужой прежний сбой также не превращается в зелёный результат: объяснить происхождение и согласовать дальнейший путь, не чиня несвязанные части молча.

Оговорки доступности платформ остаются такими, как определено в PLAN: P15 требует готовую матрицу и доступные локальные результаты, P17 — доказательства всей заявленной поддержки. Изменить обязательный критерий может явное решение пользователя, не удобство агента.

### Чего не требовать ради видимости качества

Не устанавливать произвольный процент покрытия вместо проверки рисков. Не писать тесты на каждое присваивание и на точный текст внутренней ошибки без пользовательского контракта. Не подключать все линтеры одновременно. Обязательная база — форматирование, vet, тесты и сборка; дополнительный инструмент должен находить реальную категорию дефектов этого проекта.

## Ревью и передача

Проверяющий читает изменения, воспроизводит важные сценарии и запускает необходимые проверки самостоятельно. Изучить:

- Требование → реализация → тест: можно ли проследить каждую существенную новую возможность?
- Соответствуют ли файлы/пакеты своей ответственности и направлению зависимостей?
- Одна ли реализация бизнес-правила обслуживает CLI и hooks?
- Есть ли необоснованные интерфейсы, глобальное состояние или новые зависимости?
- Верно ли обработаны отмена, ошибка Git, конкурентная запись и восстановление?
- Выполнены ли применимые принципы Go-эталона, а отклонения объяснены?

В отчёте указать конкретные файлы/символы и последствия проблемы. Формулировка «не по Clean Architecture» без нарушения согласованной границы не является достаточным замечанием. Ошибка или отсутствие обязательного теста блокируют приёмку. Пожелания, не влияющие на критерии, пометить отдельно.

Исполнитель завершает передачу только после необходимых тестов; проверяющий открывает следующий этап только после подтверждённой приёмки. Статус, команды и замечания сохраняются в PLAN.md. Этот файл не ведёт второй журнал прогресса.
